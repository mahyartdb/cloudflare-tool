# cftool — GUI Spec

- Status: Draft v1 (spec phase)
- Date: 2026-11-16
- Depends on: `00-vision.md`, `01-architecture.md` (§3.1, §3.3, §5, §7), `04-cli.md` (mock hook, error copy); module specs for option and finding-column declarations

Pinned to 0.9 deliberately: every API this spec relies on — the `Root` window root (§1, §2), `Theme::update` (§2), the rem-based/no-raw-hex rules (§2), `TableDelegate::render_td` with its `cell_label`/`row_label` labels (§3.1), and `#[gpui_kit::test]` behind the crate's `test-support` feature (§7) — was verified against 0.9.1's own documentation. gpui-kit 0.10.0 was published the same day, so the bump rule is explicit: before any bump to 0.10, every one of those claims is RE-VERIFIED against the pinned version's own documentation — the 0.10.0 crate docs, not the live site — and the pin (this line, plus the `0.9` dev-dependency in §7) is updated in the same change. The app depends on the single crate `gpui-kit`; GPUI, `base`, `component` and `assets` are re-exported from it — no separate `gpui` dependency, no git pin.

## 1. Shell

**Sidebar workspace** (persistent navigation beside a changing detail view):

```
┌──────────────────────────────────────────────────┐
│ TitleBar: cftool                    — □ ×        │
├───────────┬──────────────────────────────────────┤
│ Sidebar   │  Detail view (active module)         │
│ cftool    │                                      │
│ ● WARP    │                                      │
│ ● CDN     │                                      │
│ ────────  │                                      │
│ Settings  │                                      │
│ About     │                                      │
├───────────┴──────────────────────────────────────┤
│ StatusBar: idle / scanning 1,024 · 512 alive     │
└──────────────────────────────────────────────────┘
```

- Window root is gpui-kit `Root`: every window is built with `Root` as its root view so dialogs, notifications and theming are enabled (gpui-kit requirement, not optional).
- Sidebar nav items are generated from the frontend module registry (`ModuleMeta`): adding/removing a module updates the sidebar with zero GUI-code edits. Custom `TitleBar` (drag region preserved; native window controls on Windows). `StatusBar` shows engine state (idle / running counters / last error). Sidebar selection persists to `[gui].last_module` (§3.2).
- Sidebar width is bounded: min 12rem, preferred 14rem, max 20rem; it is fixed (not user-resizable in v1). A module name that does not fit truncates with an ellipsis and reveals its full text in a `Tooltip`, so a long name never pushes the detail view.
- Layout: detail `flex_1().min_w_0()`; row uses `items_stretch()` with full-height columns (gpui-kit coding-guide rule); the only scrolling region is the detail view's content where it overflows — never the window.

## 2. Theme (own styling, tokenized)

- Dark mode default, light available. The mode is a `Switch` in Settings — it takes effect immediately (the one exception to form controls committing at Start, §3.1) — and persists to `[gui].theme` (§3.2).
- The cftool look is one custom theme applied through `Theme::update(cx, |theme| …)` in a single `theme.rs`; `Root` is the window root, so the theme also reaches dialogs and notifications: warm orange `primary` (Cloudflare-adjacent), standard semantic roles otherwise, slightly larger `radius`, custom accent for `sidebar` surface. **No raw hex/rgb in any view file** — colors exist only in `theme.rs` (gpui-kit design-guide rule; the theme definition is the one audited exception). Built against the single `gpui-kit` 0.9 dependency (header); no separate GPUI or styling crate.
- All layout via rem-based helpers (`gap_*`, `p_*`, `text_sm`); no `px(...)` outside the theme file. Density: medium default; `small` controls in the toolbar row.

## 3. Views

### 3.1 Module view (generic, one for every module)

There is one generic module view, not one hand-built view per module. It is driven only by the module's declared metadata: `ModuleMeta` (name, description), `OptionsSpec` (arch §5), the module's declared finding columns (`columns() -> &[ColumnSpec]`, arch §5, rendered in declared order; each finding projects through `to_row()` to exactly those keys, arch §4), `actions: &'static [ActionSpec]` and `dialogs: &'static [DialogSpec]`. `ModuleMeta.actions` is what lets a module add a view action without a GUI branch: `ActionSpec { id, label, kind }`, whose single v1 kind is `OpenDialog { dialog }` — the view renders the declared actions in declared order (action row below) and opens the dialog the owning module declares under that id, rendered by the one generic dialog from its `DialogSpec { id, title, fields, confirm_command }` (`01-architecture.md` §5, §3.3). A new crate + one `.register(...)` line therefore appears in the sidebar with a working form, its declared actions and dialogs, and a results table with zero GUI-code edits (vision P1); removing the registration removes the sidebar entry. A module-specific view may be contributed later; v1 is generic-only.

- **Header:** module name + one-line description (from `ModuleMeta`).
- **Options form:** `Form`; one field per `OptionsSpec` entry: `Select` for enums (pool, port-mode, noise preset), `NumberInput` for numbers with min/max validation from the spec, `Checkbox` for booleans (scan options commit at Start — `Switch` is reserved for settings that apply immediately, §3.2), `Input`/`Textarea` for lists, spec help text inline. Advanced options collapsed under an `Accordion` ("Advanced"); defaults visible, not hidden.
- **Action row:** `Start scan` (primary — the view's one primary commitment), then the module's declared actions in declared order (`ModuleMeta.actions`), each a default-variant `Button` labelled with its `ActionSpec.label`. A kind the row can act on is resolved from the declaration alone: `OpenDialog { dialog }` opens the owning module's declared dialog with that id (§3.3 for `identity`). The row holds no `id ==` branch, so a module that declares an action appears with it and no GUI edit. While running Start becomes `Cancel` in the default (secondary) variant: cancelling is reversible (re-run), so it is not danger-styled; danger is reserved for destructive commitments, of which v1 has none.
- **One scan at a time:** Start is disabled in every module view while any scan runs, with the reason visible ("a scan is already running" — `Tooltip` and inline text). The engine's process-wide permit (arch §3.3, vision §3.1) is the backstop: a second start's run returns `ScanError::Busy`, which the view surfaces (§4), so two 512-concurrency scans never overlap.
- **Progress region (running):** `Progress` bar (completed/total endpoints, i.e. `probed`/total), counters (alive endpoints · elapsed), rolling top-5 interim results by RTT. Every running counter counts endpoints (`address:port`) — the probe unit — never addresses; a single address with four ports contributes four endpoints. The denominator is `plan_endpoints` (`01-architecture.md` §5). A probe is one endpoint's measurement (1..4 attempts), so `probed` is endpoints attempted and `alive` is endpoints whose verdict is `Alive`, one per finding; `dead` is `probed − alive`, never serialized and never a row. `filtered` (⊆ `alive`) is not one of the running counters: the engine's progress lane carries only `completed` and `alive` (arch §3.1), and the cdn filter phase runs after the latency phase, so `filtered` is not knowable while a scan runs; it appears in the totals line once the scan completes. Core owns the 50 ms progress throttle (arch §3.1); the GUI consumes the latest already-throttled snapshot and never re-throttles.
- **Result-lane batching:** `Result` events are never dropped and never throttled (arch §3.1). The GUI coalesces arrivals and applies at most one state update + notify per animation frame; that bound is what keeps a 10k-result scan responsive.
- **Results region (running/done/partial):** a virtualized `DataTable` (virtual scrolling) — a scan can produce tens of thousands of findings, so only visible rows are built, never the full result set. The table renders the module's declared `ColumnSpec` list in declared order, with the `header` text for each key: a frontend may hide a column, but never invent one (arch §4). The table renders findings once the scan finalizes — one row per alive endpoint, alive targets only: the finalized table's row count equals `totals.alive` minus the filtered rows currently hidden (the checkbox rule below), so a user can reconcile the table against the totals line. During the Run phase, before any finding exists, the table renders PROVISIONAL rows built from `ProbeOutcome` — one per alive endpoint: the endpoint, the verdict's RTT (empty when `None`) and the verdict kind — so its row count equals the alive endpoints seen so far. A column whose value only `finalize` can compute (cdn's speed, a module's post-phase status) is empty in a provisional row. On `Done`, the finalize-produced findings REPLACE the provisional rows: the table then reconciles as above, and a provisional row is never a finding, is never serialized, and does not survive the run. gpui-kit's table text is drawn by the render callback and is not read by assistive technology, so the `DataTable` delegate must supply cell and row labels separately, built from the finding row: the column's `key`/`header` for a cell, and the row's identifying value (its endpoint/target) for the row — without them the results table is unreachable by a screen reader. Row context `Menu`: `Copy` per cell, keyed by the column's `key`.
  - *Default order:* the module's declared rank (`sort_rank`, arch §4) — ranked findings first in ascending order, unranked findings (`None`) after them; no finding is dropped from the model, and the filtered rule below governs visibility.
  - *User sorting (presentation override):* column-header sorting is available and overrides the default order only for presentation — when the user sorts by a column, rows reorder by that column and the unranked-last invariant no longer applies.
  - *Filtered findings:* the default view renders every finding except the filtered ones; filtered findings stay in the model and are hidden from the results table and from both CSV export paths (`Copy CSV`, `Save CSV…`) by default; a `Checkbox` in the results region (default off, labelled to say it includes filtered results) reveals them. "Filtered" is core's `ModuleFinding::is_filtered()` flag (arch §4) — the finding responded but the module's filter dropped it, or it fell outside the retained top-N — asked of the finding, never inferred from the module's own `status` column. An endpoint whose verdict is `Dead` is not a finding (including one cancelled after a successful try) and has no row at all; it appears only in the totals line (`probed` counts it, `alive` does not). The CLI's equivalent is the global `--show-filtered` flag (`04-cli.md` §3). The GUI and CLI CSV exports must be byte-identical for the same fixture, and that parity is asserted by a test (the CLI↔GUI parity row in `06-qa.md` §2).
- **Export row:** `Copy CSV`, `Save JSON…`, `Save CSV…` (file dialog). All three go through core's shared writer — `core::output::write_csv` / `core::output::write_json` (arch §4.1), which fixes float rendering (≤ 3 decimals, trailing zeros trimmed) and the `"\n"` terminator — so the GUI never formats a row itself, and a GUI export and a CLI export of the same fixture are byte-identical. Both CSV paths export the module's FULL declared `ColumnSpec` list — every declared key in declared order, with its declared header — never the table's visible subset: a frontend may hide a column in the TABLE only (results region above), so a hidden column is still exported and the export's column set is pinned by the module, not by the view. The CLI↔GUI byte-parity fixture therefore compares exports with filtered findings hidden on BOTH sides — the CLI's default (no `--show-filtered`, `04-cli.md` §3) and the GUI's default checkbox-off state — so the compared files carry the same row set. The JSON export matches the CLI's `--json` and always includes filtered findings: the filtered rule above governs the results table and both CSV paths only. Disabled (with `Tooltip` reason) while running or when findings are empty.
- **States (all four required):**
  - *Empty:* module description + what a scan does + Start affordance — never a blank pane.
  - *Running:* progress region sits above the results region; the previous generation's findings stay visible until the first `Result` of the new generation arrives, then the table is replaced (not merged) and updates live as results stream (batched, §4).
  - *Error:* inline `Alert` (what failed + recovery hint, same copy rules as CLI §6) + `Notification`; form stays filled.
  - *Cancelled:* partial results shown with a `Cancelled` `Badge` and the totals line noting it.

### 3.2 Settings view

- Controls: theme mode (`Switch` — applies immediately), engine defaults (concurrency default — the fallback default a module uses when its own option is unset; ceilings belong to the modules — plus scan timeout; both commit on Save), config file path display + `Open config folder` (`Button`, not a link). Save writes `cftool.toml` (arch §7).
- GUI-owned config is the `[gui]` table of the same `cftool.toml` (arch §7) — no parallel GUI store:

| Key | Type | Default | Notes |
| --- | --- | --- | --- |
| `theme` | enum | `dark` | `dark` / `light`; `Switch` applies immediately |
| `window` | geometry | platform default | position + size; clamped to the visible monitors on launch |
| `last_module` | module id | first registered | restored on launch; an unknown id falls back to the first registered module |

### 3.3 Identity dialog (warp)

- Opened from the module-declared action — warp's `ModuleMeta.actions` declares `ActionSpec { id: "identity", label: "Identity…", kind: OpenDialog { dialog: "identity" } }` (§3.1 action row) — and from About. The GUI implements one generic dialog shell and no identity dialog: on `OpenDialog { dialog }` it resolves the id against the owning module's `ModuleMeta.dialogs`, renders that `DialogSpec { id, title, fields, confirm_command }` (`01-architecture.md` §5) — its `title` and one control per declared `fields` entry — and on confirm calls that module's `run_command(confirm_command, args, cancel)` with the collected field values. The GUI's view code contains no registration or import request, no WGCF parser and no `cftool_warp` reference — the registry's `.register(...)` line (§3.1) remains the only place the frontend names a module crate — so a module's dialog is a declaration like its actions, a new module's dialog appears with zero GUI edits, and Vision S4's four-edit removal still compiles both frontends. The identity semantics stay in the module's declaration: registration and import are commands it declares, and the import form's fields — private key, peer public key, endpoint, reserved bytes — are its declared `DialogSpec.fields`, read into a registered identity as the recovery path when registration is refused (import only; v1 has no identity export). Inline error on failure, rendered from the error the declared command returns (§4). Async path: the command runs on the GUI's tokio runtime, its result is bridged to the UI context tagged with a generation id exactly like a scan's (§4), so a superseded invocation's result is discarded, and it does NOT take the scan permit — `ProbeRunner::run` remains that permit's only owner (§4).

## 4. State & async model

- **Runtime ownership:** the `gui` crate owns one dedicated multi-thread tokio runtime for engine work (arch §3.3). The engine is tokio-based; gpui-kit is not, and its entities are not `Send`. Therefore channels are consumed off the UI thread by a bridge task on the tokio runtime, and entity state is mutated only on the GPUI context.
- **Event bridge:** core's two lanes (arch §3.1) feed the bridge — the progress lane is a latest-value `watch` read, the result lane is the ordered `mpsc`. The bridge tags every event with its run's generation id and applies it on the UI context (`cx.update`); the runner never waits on the bridge, and no engine future is awaited on the UI thread. **Batching rule:** the bridge DRAINS all pending events per UI turn and applies AT MOST ONE state update plus one notify per frame — every arrival since the previous frame is coalesced into that single apply, so no event is dropped and no event waits for a frame after a frame has already applied. That coalescing is the requirement G6(b) tests (§7): a bridge that applied once per event would satisfy the lanes above and still fail the P4 gate.
- **Generation id (stale-data rule):** every run carries a process-monotonic generation id, incremented before Start. Events tagged with a superseded generation are discarded — `Result`, `Done` and `Failed` included. Previous findings are retained until the first `Result` of the new generation arrives; that result replaces the old set (never merges). Cancel-then-Start therefore leaves at most one live generation.
- `AppShell` (the view under `Root`) owns: `Entity<ModuleRegistry>`, sidebar selection, and one `Entity<ScanViewState>` per registered module, created lazily and kept alive (state survives navigation).
- `ScanViewState` holds: current options snapshot, scan status (`Idle | Running { handle } | Done | Failed | Cancelled`), `Entity<ResultsModel>`, generation id, latest progress snapshot.
- Scan execution: Start does NOT acquire the engine's scan permit — `ProbeRunner::run` is its one owner: the run takes the process-wide slot for the scan's lifetime and returns `Err(ScanError::Busy)` when it is already held (arch §3.3). The GUI starts the run and surfaces the `Busy` error the run returns (the Error state, §3.1); the frontend never takes the permit itself. Start spawns the engine task on the tokio runtime. Results stream into `ResultsModel`; the `DataTable` delegate reads it — never cloned per frame. The UI never calls probe code.
- **Window close mid-scan:** the close path is the v1 path: closing the window trips the per-scan `CancellationToken` (frontend-owned, arch §3.3), joins the engine task with a 2 s bound, and drops the runtime, which aborts the task if the join timed out (arch §3.3). Only a build with the tier-2 feature compiled in inserts a step between the trip and the join — waiting for the module to tear down its in-flight tier-2 tunnel (warp §7); no v1 build compiles that feature, so the v1 sequence is exactly trip → join → drop. The window closes and the process exits only after the join or the timeout.
- No scan logic in the GUI: the GUI calls the same `ScannerModule`/`ProbeRunner` API the CLI does. Zero business rules in view code (render helpers are presentation only).

## 5. Keyboard & focus

- Every control is reachable by keyboard with a visible focus ring: sidebar items, form fields, Start/Cancel, table headers and rows, export buttons, dialog actions. No mouse-only action.
- Enter in the form commits Start (primary commit rule).
- `Cancel scan` is a default `Button` — no destructive-confirm dialog (cancelling is reversible: re-run).
- Dialogs (`Dialog`, `AlertDialog`) trap focus and restore focus to their trigger on dismissal.
- The results table is keyboard-navigable: focus moves between rows, the focused row scrolls into view (virtualized), and header sorting is reachable from the keyboard.
- Sidebar is keyboard-navigable (`Sidebar` built-ins); the selected item shows a persistent selected state.

## 6. Platform

- Windows-first: custom `TitleBar` with native controls; window min size ~900×600; window geometry persisted in `[gui].window` (§3.2). All code stays portable (gpui-kit cross-platform); no `#[cfg(windows)]` outside TitleBar handling.

## 7. Testing

- Harness: gpui-kit's view-test harness (`#[gpui_kit::test]`) lives behind the crate's `test-support` feature. Dev-dependency: `gpui-kit = { version = "0.9", features = ["test-support"] }`; the app dependency stays plain `gpui-kit = "0.9"`.
- Mock data: the GUI's mock dev-dependencies are `cftool-core = { path = "../core", features = ["mock"] }` — the script loader; core's `ProbeSource` seam and `ScriptedProbeSource` are always compiled types, and the feature only enables reading the JSON script file (it also backs the CLI's `--mock <script>` hook, `04-cli.md` §8 T3) — and `cftool-warp = { path = "../modules/warp", features = ["mock"] }` — the scripted-identity loader: under warp's `mock` feature the warp identity seam resolves to the scripted registered identity (deterministic keys) instead of reading `identity.json`, so the module's `IdentityMissing` gate is satisfied with no network. The GUI has no CLI-style `--mock` flag; its test wiring activates the same pieces directly — it passes the scripted `ProbeSource` as the SOURCE argument of the start surface (`run(plan, source: Arc<dyn ProbeSource>, events, cancel)`, arch §3): the start surface takes the probe source, never a raw probe — the source's default implementation returns `module.probe(opts)`, so the module path is the one production path, and `ScriptedProbeSource` overrides `probe` to replay the script (arch §5.2) — and under warp's `mock` feature the identity seam resolves to the scripted identity — so G5 is hermetic. Core never depends on a module, and no GUI-only mock exists.
- **G1 — form defaults:** the form renders `OptionsSpec` defaults.
- **G2 — result rows:** the results table renders a 3-finding fixture in declared rank order.
- **G3 — states:** empty / error / cancelled states render their affordances.
- **G4 — run transition:** Start transitions to Running and is disabled while a scan runs (one-scan permit, §3.1).
- **G5 — smoke flow:** a mock scan started from the warp view streams 5 results into the table (drives the async update path end-to-end). The flow runs under the two `mock` dev-dependencies above — core's scripted probe source passed at the start surface, warp's scripted identity satisfying the module's identity gate (§3.3) without a registration call, and the plan is built from the script's targets via core's `mock` loader (`01-architecture.md` §5.2), so `totals.probed` is the script's target count — so the scan is hermetic.
- **G6 — 10k responsiveness (vision S5):** stream a 10,000-result fixture through the event bridge into the results table. Neither frames nor realized rows are measurable by observing the tree — gpui-kit's test surface has no frame counter, and `DataTable` row ids are composite — so the view under test exposes two application-level instruments, both wired in view code: an apply counter, incremented once per state application, and a realized-row set filled by the table delegate's cell hook (`render_td(row_ix, col_ix, …)`), which records `row_ix` (the same mechanism as the apply counter, not tree observation). The test asserts (a) applies ≥ 1; (b) applies < the number of injected results — coalescing happened, many results per apply; (c) after the drain, the model's row count equals the injected result count — no result lost; (d) the DISTINCT row indices recorded by the cell hook in any one apply — a per-apply set, cleared between applies, so successive applies do not accumulate — stay within the viewport's row capacity, ≪ 10,000, so only visible rows are realized. The hook is per cell, not per row: a raw call count equals applies × realized rows × columns per row, so the assertion counts distinct rows and never calls; (e) the first mock result is observable in the table state within 1 s of injection, polled with a deadline (no fixed sleep).
- **G7 — settings round-trip:** write `[gui].theme`, `[gui].window` and `[gui].last_module`, reload the persisted state, and assert the theme is restored, the window geometry is restored and clamped to the visible monitors, and an unknown `last_module` falls back to the first registered module.
- **G8 — identity dialog (new in §7):** the dialog opens from warp's declared action (`ModuleMeta.actions` → `OpenDialog { dialog }`), not from a hand-wired view path; the import fixture's form fields are rendered from the module's declared `DialogSpec.fields` (private key, peer public key, endpoint, reserved bytes); confirming invokes the declared `run_command(confirm_command, args, cancel)`; the identity it stores is accepted by the module's identity gate (`plan()` returns `Ok`, not `IdentityMissing`); and a failed confirm (an invalid fixture) renders the inline error. Method: integration — a `#[gpui_kit::test]` view test driving the dialog's async path through the UI-context bridge (§4), hermetic under both `mock` features: core's `mock` feature is the script loader for the probe source and warp's `mock` feature supplies the scripted identity, so no registration or other network call runs.
- Live-window manual QA (real mouse/keyboard) is part of the acceptance runbook (`06-qa.md` §3) — automated tests don't establish visual quality.

## 8. Non-goals (GUI)

- No dock/multi-window layouts, no chart views in v1 (results table + counters carry v1; charts are a v1.1 candidate on the results model).
- No in-GUI config-file text editing (Settings covers v1 needs).
- No dynamic module discovery UI (modules are compile-time, arch §5).
