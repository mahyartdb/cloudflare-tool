# cftool — QA, Verification & Build Order

- Status: Draft v1 (spec phase)
- Date: 2026-11-16
- Depends on: `00-vision.md`, `01-architecture.md`, `02-warp-scan.md`, `03-cdn-scan.md`, `04-cli.md`, `05-gui.md` (the full spec set; this doc closes it)

## 1. Purpose

"Done" for v1 is proven, not asserted. Every success criterion declared anywhere in the spec set maps to exactly one row of §2, one verification method, and one owning build phase. A criterion the spec set marks post-v1 keeps its row with phase `post-v1` and is not part of v1's Definition of Done. A row counts as verified only when its evidence has been observed — captured command output or a checked checklist item — never inferred from related tests passing. This doc is the build-order contract for phases P0–P5 (§4) and the acceptance contract for P5.

## 2. Acceptance matrix

Methods: **unit** = in-crate automated test; **integration** = cross-crate or binary behavior via `cargo test` or a scripted command; **ignored-live** = `#[ignore]` network test run explicitly on the developer's machine (§3); **manual-GUI** = the live-window checklist (§3). Labels C1–C6 are assigned here; `01-architecture.md` §11 names C7 directly. Every other label is the spec's own — warp's are `02-warp-scan.md` §9 T#, cdn's are `03-cdn-scan.md` §7 T#, the CLI's are `04-cli.md` §8 T#, the GUI's are `05-gui.md` §7 G1–G8. Every §2 row cites its test reference spec-qualified — `01 §11 C7`, `02 §9 T3`, `03 §7 T6`, `04 §8 T9`, `05 §7 G8` — never a bare label like `T3`: `T1`–`T10` are reused across warp, cdn and the CLI, so a bare label names no test.

Notes:

- Live rows (S2, S3, warp T4/T5, cdn T4) are authored in P1/P2 with `#[ignore]` and verified only at P5 — never assumed green earlier (§3).
- S2's time bound is T5's; its coverage half is an observation, not a gate (00 §7 S2): a side-by-side warp-plus run in the same P5 session records both tools' alive sets in a transcript; a gap is a written finding, never a failed build. The transcript is P5's exit evidence (§4.6).
- S5 splits across phases: the 1 s result bound is G6's automated assertion (P4); the 100 ms frame gap and the 500 ms Cancel are observed on a 60 fps recording (§3). The row stays P5 because Vision §7 verifies it there.
- C4 is the core test behind CLI T5's graceful Ctrl-C half (04 §8 T5); the CLI only renders what the channel emits.
- C7 is the core backstop, not a plan-time check: core owns only the 4,096 hard ceiling, enforced when the runner is constructed (`InvalidPlan`, exit 3), while each MODULE owns its own declared ceiling in `plan()`'s option validation (`OptionsInvalid`, exit 1). Core's 4,096 response to a value of 5,000 is therefore C7's `InvalidPlan`, and no v1 CLI path delivers 5,000 to core: both modules' option validation rejects it first — warp declares 4,096, cdn 512 tcp / 200 http, so each returns `OptionsInvalid` (exit 1) before a runner is constructed. cdn's 513 is that same module-side `OptionsInvalid` case (03 §7 T2), never a second `InvalidPlan` (01 §5, §9).
- The mock source is one mechanism: core's `ProbeSource` seam + scripted probe source — their TYPES are ALWAYS COMPILED, not feature-gated — and they back the CLI's `--mock <script>` hook and the GUI tests alike (04 §8 T3, 05 §7); the `mock` cargo feature gates only the script loader, and the scripted identity is warp-side, with warp's own `mock` feature enabling its loader (01 §5.2, 02 §5). Those types are P0's deliverable. Because they always compile, the tests that build the scripted source directly run in gate 4; gate 5 adds the loader- and flag-gated tests (T2's positive half, T3, T9).
- GUI "unit" rows are `#[gpui_kit::test]` view tests; G5 and G8 are classed integration because they drive the view and the async path end-to-end — G5 the scan event path, G8 the dialog's declared command and the identity it stores (05 §7, §3.3).
- Tier 2 (02 §7) is post-v1: nothing in it ships in v1, so T7 is authored post-v1 and verified in the tier-2 release — not in P1 — and a v1 build has no `--validate` flag.
- T9 is the budget-exhaustion counterpart to C4's user cancel: the mocked latencies outlast the ceiling, and the `Log` line — not the exit code — is what distinguishes it from Ctrl-C (04 §4, §6).
- T10's WGCF-format fixture is checked into the test tree and needs no network; the import writes the same `identity.json` shape the registration path writes (02 §5) and the stored identity satisfies the identity gate, which is why the import is risk (e)'s recovery path.
- G7 is the only row over the `[gui]` table both frontends share (05 §3.2); there is no GUI-only store, so the round-trip test is the settings contract.
- Two config rows split the file's key handling: T4 is an unknown key inside a registered module's table (exit 1); T8 is a whole table for a module the build does not register (warning, exit 0) (04 §8 T4, T8; 01 §7).
- T6 carries two rows because 04 §8 T6 asserts two things with two verification methods: the unit half is resolution precedence plus the resolved `total_budget` (the value the plan-time feasibility floor is checked against); the integration half is the floor rejection — exit 3 with both numbers, the requested ceiling and the required minimum, in the message.
- cdn's T6 carries two rows: extraction (a reply missing either header is a dead probe, never `colo = ""`) and the colo path (the recorded fact reaches the `colo` column and the `--cfcolo` drop) — filter and column read one field, the same rule the loss row applies to `loss_pct` (03 §7 T6; 03 §3.1, §4, §6).
- The parity row is one fixture through both frontends — the test calls each frontend's own export function (the CLI's, through `crates/cli`'s `[lib]` target that `crates/gui` dev-depends on, 01 §1; and the GUI's), and each hands the same `ScanSummary` to `core::output::write_csv` / `write_json` (arch §4.1), never to a frontend formatter — so the test writes both CSV files and compares their bytes: two real frontend calls, never two core calls. Both CSV exports carry the module's full declared `ColumnSpec` list — every key in declared order, with its declared header — whatever the table hides, and both are written with filtered findings hidden (the CLI's default, the GUI's checkbox-off), so the compared row sets match; for JSON, both sides always include filtered findings (the CLI's `--json`, the GUI's JSON export), so a JSON comparison covers the full finding set. It is the one P4 row that crosses crates, which is why it is classed integration.

### 2.1 Exit codes

Authoritative table is `01-architecture.md` §8; `04-cli.md` §6 is the CLI's copy. Rows and checklist items in this doc assert these codes, not their own.

| Code | Meaning |
| --- | --- |
| 0 | success (findings may be empty) |
| 1 | invalid options or config |
| 2 | usage / argument-parse error — the argument parser's own, never a `ScanError` |
| 3 | plan or validation error (allowlist violation, invariant breach) |
| 4 | network or runtime error |
| 5 | cancelled — by the user (Ctrl-C, Cancel) or by budget exhaustion; graceful, partial summary still emitted |
| 6 | internal error (`ResultLaneOverflow`, `Internal`) |
| 130 | hard exit — second Ctrl-C only |

- `ScanError` mapping: `OptionsInvalid` → 1; `InvalidPlan` / `AllowlistViolation` / `IdentityMissing` → 3; `Network` / `Busy` / `RegistrationRejected` → 4; `Cancelled` / `BudgetExhausted` → 5; `ResultLaneOverflow` / `Internal` → 6.
- Ctrl-C pair (04 §4, §6): first press → 5 with partial output; second press → 130 with no summary. Both are checklist items (§3).
- Budget exhaustion — the resolved wall-clock ceiling reached mid-scan — ends the scan the same way a user cancel does: no probe starts after the ceiling, in-flight probes are aborted at their next await (`04 §4`), the partial `ScanSummary` is emitted with `totals.cancelled = true`, a `Log` line names the reason, and the process exits 5. The stop completes within 500 ms of the ceiling being reached — the same bound as a user cancel (Vision S5), and reachable only because probes abort at their next await rather than draining to the per-attempt cap.

## 3. Verification gates

The gate sequence, exact and in order, run at the repo root over the whole current workspace (the workspace grows each phase; gates always cover all of it):

```text
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo check --workspace
cargo test --workspace
cargo test --workspace --features mock
```

All five green in sequence = "gates green" in every phase's Done (§4). Warnings are errors; a phase is not done with any gate failing or skipped. The five gates are run on cargo/rustc 1.97.1 — the current reference toolchain. §4.1's `rust-version = "1.97"` is the floor the code must build on — the workspace manifest's declared MSRV (matching `01-architecture.md` §10) — and 1.97.1 satisfies it; the run toolchain is stated here because the uniformity claim below is a property of it.

The fourth and fifth gates split the suite by what the `mock` feature gates, not by taste. Core's mock TYPES — the `ProbeSource` seam and the scripted probe source (01 §5.2) — are always compiled: they are ordinary core code, so every test that builds the scripted source directly runs in gate 4. The cargo feature `mock` on `cftool-core` enables only the SCRIPT LOADER (reading the JSON script file); the CLI's own `mock` feature forwards it and `cftool-warp`'s scripted identity and compiles the `--mock` flag, and the scripted IDENTITY is warp-side — the identity artifact and the `IdentityMissing` gate belong to the warp module, so warp's own `mock` feature enables the scripted-identity loader (01 §5.2, 02 §5). Gate 4 (`cargo test --workspace`) therefore runs the tests that need no loader; gate 5 (`cargo test --workspace --features mock`) additionally runs the loader- and flag-gated ones (CLI T2's positive half, T3, T9). A crate that does not expose the feature ignores the flag — the command still succeeds — so the sequence stays uniform as the workspace grows. That flag-ignoring behavior was reproduced empirically on cargo 1.97.1, the reference toolchain named above; on any other toolchain it is an assumption, not an observation.

Live tests: `#[ignore]`-marked tests compile under `cargo test --workspace` but never run in it or in CI. They run explicitly, on the developer's machine only:

```text
cargo test -p cftool-warp -- --ignored
cargo test -p cftool-cdn -- --ignored
```

If CI is introduced, it runs the gates only; a green CI run never implies live tests or manual QA passed.

Manual-GUI QA checklist (live window, real mouse/keyboard; automated GUI tests do not substitute for it — 05 §7). Each item is observed, not assumed:

1. **Keyboard path through a scan** — reach a module view, change one option, Start via Enter, read progress, Cancel: no mouse (05 §5).
2. **Focus restore after dialogs** — identity dialog and Save dialogs return focus to their trigger on dismissal (05 §5).
3. **All four module-view states** on both warp and cdn views: Empty, Running, Error (induced via a deliberately invalid option — warp: a non-CF custom CIDR; cdn: tcp `concurrency` 513 → `OptionsInvalid`), Cancelled (05 §3.1).
4. **Both themes** — dark default and light: every view legible; colors only from `theme.rs` (05 §2).
5. **Zoom at 2 base-font sizes** — default and one larger: no clipped text, no broken layout (detail view keeps `min_w_0`, 05 §1).
6. **Min window size** ~900×600 (05 §6): sidebar, detail, and status bar intact at minimum.
7. **Vision S5 responsiveness** — `cdn-scan --sample-per-subnet 2 --timeout 330` over the published v4 ranges (11,912 targets; the plan's floor at that size is 300 s = ceil(11,912 / 200) × 5 s, the 5 s being the cdn tcp per-probe cost: 1 s warm-up + 4 × 1 s attempts), recorded at 60 fps: no frame gap > 100 ms while results stream; a finished probe's result visible within 1 s; Cancel halts the scan within 500 ms and the view shows partial results with a `Cancelled` badge.
8. **Ctrl-C pair (CLI)** — during a scan: first press → partial summary rendered, `totals.cancelled: true`, exit 5; second press → immediate exit 130 with no summary on stdout. On Windows the default console handler exits with `STATUS_CONTROL_C_EXIT`, so the contract needs a console control handler that counts presses and exits 130 on the second (the one permitted `windows`-crate use, 01 §10); the first press still exits 5 with the partial summary.

## 4. Build order
