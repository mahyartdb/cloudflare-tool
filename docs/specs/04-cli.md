# cftool — CLI Spec

- Status: Draft v1 (spec phase)
- Date: 2026-11-16
- Depends on: `00-vision.md`, `01-architecture.md`; module specs for option semantics

## 1. Binary

`cftool` — single static exe (crates/cli). Windows-first (qmahyar), portable code. Subcommands mirror the module registry; unknown/missing module subcommands are impossible by construction (help is generated from the registry).

## 2. Command surface

```text
cftool <module-scan> [options]        # one subcommand per registered module (naming rule below)
  cftool warp-scan [opts]
  cftool cdn-scan [opts]
cftool modules                        # list registered modules + version + description
cftool config init                    # write a commented cftool.toml template
cftool config path                    # print the resolved config file path
cftool ranges refresh                 # refresh Cloudflare range cache (core facility)
cftool warp identity register         # declared by the module, rendered (warp spec §5)
  cftool warp identity import <file>  # WGCF-format config import (recovery when registration is refused)
  cftool warp identity show
```

Naming — the module id, the CLI name, and the config key are three different things, one rule each:

| Artifact | Rule | Example |
| --- | --- | --- |
| module id | `ModuleMeta.id`; also the config key and the group prefix | `warp` |
| CLI subcommand | `<id>-scan` by default; `ModuleMeta.cli_name: Option<&'static str>` overrides it when `Some` | `warp-scan` |
| subcommand group | `cftool <id> <group> <cmd>` — always the module id, never the CLI name | `cftool warp identity register` |
| config table | `[modules.<id>]` | `[modules.warp]` |

- The identifiers are independent: `cli_name` changes only the CLI subcommand — never the module id, config table, or group prefix.
- `--help` at top level lists module subcommands with their descriptions (from `ModuleMeta`) plus `config`, `ranges`, and module subcommand groups. Per-subcommand `--help` renders the module's `OptionsSpec` (arch §5) — one source of truth, no hand-maintained help duplication.
- Module-owned subcommand groups (like `warp identity`) come from the module's `ScannerModule::subcommands()` accessor (arch §5 — the trait method is the single source; there is no copy on `ModuleMeta`). Each `SubcommandSpec` declares the command's name, description and args — `subcommands()` returns `&[SubcommandSpec]` with `args: &'static [OptionSpec]` (`01-architecture.md` §5) — so the CLI renders the group, each command's flags and each command's `--help` from that metadata: the concrete spellings in the surface block above (`register`, `--force`, `import <file>`, `show`) are what warp's declaration renders to and belong to `02-warp-scan.md` §5, never to a fixed list in this document. Parsed values enter the module's option map by declared key, and dispatch is the trait's `run_command(id, args, cancel)` on the declared name alone; the CLI names no module crate, command or arg in its own code, so a module's command surface can change — or the module crate can leave the build (Vision S4) — with no CLI edit. v1: only warp declares a group.
- `cftool warp identity import <file>` reads a WGCF-format config — private key, peer public key, endpoint, reserved bytes — and writes `identity.json`. It is the recovery path when registration is refused (`02-warp-scan.md` §5). Import only: no config export (Vision N2).
- `config init` / `config path` are core facilities, not module subcommands; `config path` prints the same path `--config` overrides (§5).
- Global flags: `--config <path>` (override config file), `--json` (machine output), `--csv <path>` (write CSV; `-` = stdout), `--show-filtered` (include filtered findings in table/CSV, §3), `--quiet` (progress off), `--verbose` (Log events to stderr), `--timeout <s>`, `--version`, `--help`.
- `--mock <script>` is a global flag, compiled only when the CLI crate's `mock` feature is enabled — that feature forwards `cftool-core`'s script loader and `cftool-warp`'s scripted identity (`01-architecture.md` §5.2), and a release build never carries flag or loader. `<script>` is a JSON file path; the authoritative grammar is `01-architecture.md` §5.2 — `{ targets: [{ ip, port, verdict, rtt_ms }] }`, one entry per scripted target in probe order, where `verdict` is `alive` | `cookie` | `dead`, `rtt_ms` is required only for `alive` (a cookie reply has no timing, so it carries none), and `{ ip, port }` is a `ProbeTarget`. The scripted probe consumes wall-clock `rtt_ms` per target before returning its verdict, so a scripted scan can be made to outlast a ceiling on purpose (T9). When supplied, the script REPLACES the plan's target set: the scan probes exactly its `targets`, so `totals.probed` equals the script's target count. The script does not affect plan validation, which still runs over the plan's own target set before any probe (§8 T2). T2/T3.
- `--timeout <s>` is a wall-clock ceiling for the whole scan (engine `total_budget`, arch §3). Resolution, highest first: `--timeout` (CLI flag) → the module's own `scan-timeout` option given on the CLI → `[modules.<id>] scan-timeout` in the config file → `[engine] scan-timeout` → the module's default. `--timeout` overrides `--scan-timeout` when both are given. Whatever the chain resolves, the frontend writes that ceiling into the module's `scan-timeout` option value inside `ModuleOptions` before calling `plan()` — it is the same number the engine enforces as `total_budget`. Every module declares `scan-timeout` in its `OptionsSpec` (`warp` 90 s, `cdn` 180 s — `02-warp-scan.md` §6, `03-cdn-scan.md` §5), statically defaulted so the key is always present in `ModuleOptions` (`01-architecture.md` §5 has no absent-key case for it), so the module's declared default is the chain's floor and no branch of the chain can fall through to a ceiling-less scan.
- The module's own feasibility floor is validated against that written value (`02-warp-scan.md` §6 for warp, `03-cdn-scan.md` §5 for cdn; the floor formula belongs to the module — this document states no generic one): if the resolved ceiling is below the floor, `plan()` returns `InvalidPlan` and the command exits 3 before any probe starts — never a silent clamp. Worked example: `cftool warp-scan --timeout 10` resolves the ceiling to 10 s; the default warp plan's floor is 7 address-waves × 1 port × `per_probe_timeout` ≈ 10.7 s (the probe's total cap under the probe time model, `01-architecture.md` §5), so `plan()` returns `InvalidPlan` and the command exits 3 with both numbers in the message — the resolved ceiling (10 s) and the required minimum (≈ 10.7 s). T6 pins both the order and the floor check.

## 3. Output

- **One writer, core-owned:** the CLI formats no rows itself. `--csv` and `--json` both go through core's shared writer — `core::output::write_csv(columns: &[ColumnSpec], rows: &[FindingRow], out: &mut impl Write)` and `core::output::write_json(summary: &ScanSummary, out: &mut impl Write)` (arch §4.1) — so a CLI export and a GUI export of the same fixture are byte-identical: the GUI calls the same writer. The CLI picks the rows (the filtering rule below); every cell, header and separator comes from core. The rendering rules live in core, not in either frontend: a `CellValue::Number` renders with at most 3 decimals and trailing zeros trimmed (`12`, `12.5`, `12.125`), text renders as-is, and the line terminator is `"\n"` on every platform — never CRLF. The CLI's export path is a function in `crates/cli`'s `[lib]` target (`01-architecture.md` §1); the P4 parity test lives in `crates/gui`, which dev-depends on that library and calls the function, so the CLI's own manifest names no frontend dependency.
- **Default (TTY):** live progress — one status line (completed/total, alive count, elapsed) plus a rolling top-5 list of the best findings by RTT (the GUI shows the same; `02-warp-scan.md` §8 says both frontends do), refreshed in place, then a results table on completion. During the Run phase that top-5 cannot be read from `findings` — findings exist only after `finalize` (`01-architecture.md` §4) — so it is built from PROVISIONAL rows projected from `ProbeOutcome`: the endpoint, the verdict's RTT, and the verdict kind, the same projection the GUI uses; a verdict with no RTT (a cookie reply) is listed with no timing. The final table on completion is the finalize-produced findings, which replace the provisional rows. Columns are the module's declared `ColumnSpec` (arch §5): it fixes order, headers, and which finding fields render; this document names no module columns. Rows are best-first in ascending `sort_rank`: `Some(rank)` rows rank ascending, `None` rows are unranked and listed after every ranked row, and no row is ever dropped from `findings` — filtered rows are hidden from table/CSV only by the `--show-filtered` rule below. Tables use the `tabled` crate; no color when not a TTY.
- **Filtered findings:** the default table and CSV show every finding except the filtered ones; `--show-filtered` adds them; `--json` always includes them. "Filtered" is core's `ModuleFinding::is_filtered()` flag (arch §4) — the finding responded but the module's filter dropped it (over max-rtt, under min-rtt, over max-loss, colo mismatch) or it fell outside the retained top-N — so the frontend asks the finding for that flag and never parses the module's own `status` column, whose vocabulary stays the module's. Filtered findings stay in `findings` and so remain in JSON. An endpoint whose verdict is `Dead` is not a finding (including one cancelled after a successful try) and never appears as a row in any output — not the table, not the CSV, not the JSON `findings` list; it is visible only through the totals, where `probed` counts it and `alive` does not. T7.
- **`--json`:** one JSON document on stdout: `{ module, started_at, wall_time, totals { probed, alive, filtered, cancelled }, findings: [...] }` — core's `ScanSummary` serde form (arch §4): the serialized summary key is `module` (Rust field `module_id`, renamed in the hand-written `Serialize` impl), `started_at` is RFC 3339, `wall_time` is an integer number of MILLISECONDS (the impl converts the `Duration`, so serde's `{secs, nanos}` default never reaches the document), and `totals` is exactly `{probed, alive, filtered, cancelled}` — `probed` counts ENDPOINTS attempted, `alive` is the number of findings — endpoints whose verdict is `Alive` — and `dead` (`probed − alive`) is a core-internal counter that is not serialized. An endpoint is `(address, port)`: for cdn an address and an endpoint coincide, while for warp in `standard` mode one address yields up to four endpoints. `filtered ⊆ alive`, counting findings whose `is_filtered()` is true. Finding fields are the module's (02 §8, 03 §6). Progress events go to stderr; stdout stays pure for piping.
- **`--csv <path>`:** the module's `ColumnSpec` headers plus each finding's `to_row()` cells (arch §4), one row per finding, same filtered-finding rule as the table. `--csv -` writes stdout (mutually exclusive with `--json`).
- Exit codes (§6) and stderr messages follow the same summary/finding model, so scripts only parse stdout.

## 4. Progress & cancellation

- Ctrl-C, first press: cancel gracefully (`CancellationToken`) — the engine stops starting probes, in-flight probes are ABORTED at their next await (not drained to completion), and the partial `ScanSummary` is emitted and rendered per §3 with `totals.cancelled: true`; then exit 5. "Aborted at the next await" is the engine's committed semantics: the token is observed at every await, so the scan stops within 500 ms of the token firing (`01-architecture.md` §11, Vision S5) even when a probe's per-attempt timeout is 1 s.
- Ctrl-C, second press: hard exit — no summary, no partial output; exit 130. On Windows the default console handler terminates the process with `STATUS_CONTROL_C_EXIT` (0xC000013A), not 130, so this contract requires a console control handler that counts presses and exits 130 on the second — the one permitted `windows`-crate use (`01-architecture.md` §10). The first press still exits 5 with the partial summary; the handler exists to count the second press without letting the default handler kill the process.
- **Budget exhaustion:** reaching the resolved wall-clock ceiling mid-scan stops the scan the same way — the engine stops starting probes, in-flight probes are aborted at their next await, the partial `ScanSummary` is emitted and rendered per §3 with `totals.cancelled: true`, a `Log` line names the reason (the resolved ceiling that was reached), and the command exits 5. That is the same code as a user cancel; the two are distinguished by the `Log` reason, not the code. The plan-time floor (§2) normally makes this rare. T9.
- Progress events are read from the progress `watch` lane — latest snapshot wins, intermediate values dropped by design — while results arrive on the ordered `mpsc` result lane (arch §3.1); the status line updates at most every 50 ms (throttle is in core, CLI just renders).

## 5. Config file

- `cftool.toml` in the platform config dir (arch §7). `--config` overrides location; `cftool config path` prints the resolved path.
- CLI flags override config values. Unknown keys (typo protection): a key not present in a *registered* module's option spec, or an unknown `[engine]`/`[gui]` key, is an error naming the offending key (exit 1). A `[modules.<id>]` table whose `<id>` is not in the current build's registry is ignored with a `Log` warning and never fails the config — that is what keeps Vision S4 (remove a module crate) from breaking an existing `cftool.toml` (arch §7). T8.
- Module options live under `[modules.<id>]`, engine settings under `[engine]` — ids per §2's naming rule. `[engine]` keys: `scan-timeout` participates in `--timeout` resolution (§2); `concurrency` is the fallback default for a module that exposes a `concurrency` option — module option given on the CLI → `[modules.<id>] concurrency` → `[engine] concurrency` → the module's default; `output_dir` is reserved and has no effect in v1 (CSV goes to `--csv <path>`; the GUI uses file dialogs).
- Never auto-generated: `cftool config init` writes a commented template. (Explicit > magic.)

## 6. Exit codes

| Code | Meaning |
| --- | --- |
| 0 | success |
| 1 | invalid options or config |
| 2 | usage / argument-parse error (clap's own default) |
| 3 | plan or validation error (allowlist violation, invariant breach) |
| 4 | network or runtime error (no route, DNS failure, registration failure) |
| 5 | scan cancelled by the user, or the wall-clock budget exhausted (partial results still emitted) |
| 6 | internal error |
| 130 | hard exit (second Ctrl-C) |

- `ScanError` mapping (arch §8): `OptionsInvalid { .. }` → 1; `InvalidPlan` / `AllowlistViolation` / `IdentityMissing` → 3; `Network` / `Busy` / `RegistrationRejected { status, api_version }` → 4; `Cancelled` / `BudgetExhausted` → 5; `ResultLaneOverflow` / `Internal` → 6. T5.
- **Module ceiling vs core's backstop:** a value above the module's own declared ceiling is `OptionsInvalid` from `plan()`'s option-validation step — the first of `01-architecture.md` §3's four checks — so it exits 1; BOTH `cftool cdn-scan --concurrency 513` and `--concurrency 5000` exit 1 for cdn (both exceed cdn's 512 tcp / 200 http ceiling; the value never reaches core). Core's 4,096 backstop returns `InvalidPlan` → exit 3, and is exercised only by C7 constructing the runner directly (`01-architecture.md` §5, §11) — no CLI invocation through a correctly declared module can reach it.
- **Exit 5: the summary flag first, the error as fallback:** a graceful stop produces a summary with `totals.cancelled = true` — a user cancel and a budget exhaustion both end with `Done(ScanSummary { totals.cancelled: true, .. })` — and the CLI derives exit 5 from that flag. Only when no summary could be produced at all does the `ScanError` decide the code: the result-lane receiver was dropped before `Done` could be enqueued (`Err(Cancelled)`, `01-architecture.md` §3.1), or the budget expired before any summary could be produced (`Err(BudgetExhausted)`) — the CLI maps those two to exit 5 as the no-summary fallback. So the variant mapping above is T5's unit contract and a fallback, never the graceful stop's code path; `BudgetExhausted` has exactly one constructor, that no-summary case, while a budget stop with results returns `Ok(summary)` with `totals.cancelled = true` (§4). `Failed` is emitted only for a hard failure with no usable summary (`01-architecture.md` §3.1).
- Budget exhaustion (§4) exits with the same code as `Cancelled` (5) and the same derivation, with partial results; the `Log` line naming the resolved ceiling is what distinguishes it from a user cancel — never the exit code. A resolved ceiling below the plan's floor exits 3 instead (plan error, §2).
- A failure writing an output file (`--csv` to an unwritable path) is a runtime error, not a `ScanError`: exit 4, printed as `error: could not write <path> — <cause>`.
- 2 is clap's own parse/usage exit; the CLI does not remap it. 0 means the command completed — findings may be empty.
- 130 only on the second Ctrl-C (§4); the first press is always 5.
- Errors print `error: <what failed> — <likely cause at caller's level>` + a `next step` hint line when one exists (e.g. allowlist violation suggests `--pool default`). No stack traces unless `--verbose` (then full `anyhow` chain).

## 7. UX details

- Registration flow (`warp identity register`) prints non-interactive progress and the stored identity path; never echoes keys to stdout in full (mask middle bytes in `identity show`).
- `--quiet` suppresses progress but not results/errors.
- Help text ends with the non-affiliation/ToS notice (one line, not a lecture), shown once by the top-level `--help`; subcommand help does not repeat it. T1.
- Windows console: enable UTF-8 output + virtual terminal processing at startup (behind `#[cfg(windows)]`); degrade gracefully.

## 8. Testing

- T1: integration — command surface: `cftool modules` lists both modules with metadata; top-level `--help` lists `warp-scan`, `cdn-scan`, `config`, `ranges`, and the `warp identity` group; the non-affiliation notice appears once in top-level help and not in subcommand help.
- T2: integration — plan validation: `cftool warp-scan --cidr 192.0.2.0/31` (TEST-NET-1) → exit 3, stderr names the allowlist, and no network traffic occurs (the plan error precedes the run phase; no probe starts); supplying `--cidr` implies `pool=custom`, so the command as written is valid input and fails on the allowlist, not on an unknown or conflicting option. Positive half (`cargo test -p cftool --features mock`): `cftool warp-scan --mock <script>` validates the default warp plan with no allowlist error and exits 0 without probing — the script carries an empty `targets` array, and validation covers the plan, not the script (§2). This half needs only the scripted identity to pass the warp identity gate: that seam is warp-side (`02-warp-scan.md` §5), and the CLI's `--mock` flag implies it, so the test runs with no network on a machine that has never registered.
- T3: integration (`cargo test -p cftool --features mock`) — `--json` on a scripted 3-target scan emits one `ScanSummary` document with exactly the §3 top-level fields, a four-field `totals`, a `started_at` that parses as RFC 3339, a `wall_time` that is a JSON integer count of milliseconds (never an object), `totals.probed == 3`, and 3 findings. The script supplies those targets — `{ targets: [{ ip, port, verdict, rtt_ms }] }`, §2 — and a supplied script REPLACES the plan's target set, so the scan probes exactly the script's 3 targets and `totals.probed` equals the script's target count. One mock mechanism, shared: the `ProbeSource` seam and `ScriptedProbeSource` in `cftool-core` are always compiled — the `mock` cargo feature enables only the JSON script loader — and `cftool-warp`'s `mock` feature provides the scripted registered identity (deterministic keys, no network), so the warp identity gate is satisfied under `--mock` and the scan runs hermetically. The CLI forwards both features and compiles `--mock <script>` only when they are on, so release builds never carry the flag. The GUI test path needs no gated probe source: the always-compiled `ScriptedProbeSource` from `cftool-core` is constructed directly in the test; the `mock` feature is only needed for the file loader, and the CLI's `--mock` flag is compiled only under it (05 §7).
- T4: integration — config: unknown key → exit 1 with the key named; `cftool config init` writes a template that parses; `cftool config path` prints the file `--config` resolves to.
- T5: unit — every `ScanError` variant maps to its §6 code; graceful Ctrl-C is core's cancellation test (the CLI renders whatever the channel emits, not separately integration-tested).
- T6: unit (resolution) + integration (floor) — timeout resolution (§2): `--timeout` beats `--scan-timeout`; module option beats config; the module's own default is the chain's floor when nothing else is set; assert the resolved `total_budget` and that it is the value the plan-time feasibility floor is validated against. Floor rejection: when the resolved ceiling is below the module's feasibility floor, `plan()` returns `InvalidPlan`, the command exits 3 with BOTH numbers in the message (the resolved ceiling and the required minimum), and no probe starts — the §2 worked example (`--timeout 10` against warp's ≈ 10.7 s floor) is the concrete case.
- T7: unit — output filtering, dead endpoints and columns: a fixture summary with 2 filtered and 1 ok finding renders 1 table row and 1 CSV row, with table headers matching the fixture module's declared `ColumnSpec` (order and headers); `--show-filtered` renders 3 table rows and 3 CSV rows; `--json` always carries 3 findings. A second fixture adds an endpoint whose verdict is `Dead` (no finding) to that summary: it adds no row to the table, the CSV, or the JSON `findings` list, in either mode, while `totals.probed` counts it (4) and `totals.alive` does not (3).
- T8: integration — stale module config: a `cftool.toml` containing `[modules.cdn]` loads with exit 0 and exactly one `Log` warning when the test build's registry does not include cdn; the same file with cdn registered loads with no warning and exit 0, and an unknown key inside that table then exits 1 naming the key. The same test asserts an unknown `[engine]`/`[gui]` key exits 1 naming the key.
- T9: integration (`cargo test -p cftool --features mock`) — budget exhaustion, on a ONE-WAVE custom plan rather than the default warp plan, because the test's ceiling is pinned from below by the plan's feasibility floor (§2): `cftool warp-scan --cidr 188.114.96.0/24 --mock <script>` with `--timeout 2`. `--cidr` implies `pool=custom` (§2 T2), so the plan is 256 addresses on the default `pinned` port-mode = 256 endpoints — all inside the 512-endpoint concurrency, hence 1 address-wave — and its floor is 1 × 1 × 1.525 s ≈ **1.525 s** (`02-warp-scan.md` §6), so a 2 s resolved ceiling clears the floor and `plan()` accepts; the default plan's floor (≈ 10.7 s, §2) would force any accepted ceiling above ≈ 10.7 s and burn ~11 s of wall clock per run. The script-supplied targets replace the plan's set (as in T3, §2) and their scripted latencies outlast that 2 s ceiling, so the scan stops at the resolved ceiling (2 s), emits the partial `ScanSummary` with the results collected so far and `totals.cancelled: true`, logs one line naming the resolved ceiling, and exits 5 (derived from `totals.cancelled`, §6) — the test costs ~2 s, not ~11 s. Independently, a plan whose resolved ceiling is below its feasibility floor never starts a probe (exit 3, the §2 worked example).
- T10: integration — identity import: importing a WGCF-format fixture writes `identity.json` with the private key, peer public key, endpoint and reserved bytes; `cftool warp identity show` masks the key; the stored identity then satisfies the module's identity gate (no network involved).
