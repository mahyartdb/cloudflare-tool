# cftool — warp-scan Module Spec

- Status: Draft v1 (spec phase)
- Date: 2026-11-16
- Depends on: `00-vision.md`, `01-architecture.md`
- Evidence base: `docs/research/scanner-landscape.md` §2.1–§2.5, §2.7, §4–§5 (source-verified claims carry the same file citations there)

## 1. Purpose

`warp-scan` probes Cloudflare WARP endpoint pools with real WireGuard Noise_IKpsk2 handshake initiations from a legitimately registered WARP identity, ranks live endpoints by measured handshake RTT, and (tier 2, post-v1 — §7) validates finalists in-tunnel so filtered networks don't report endpoints that die after one handshake.

The naive-probe lesson is load-bearing: WARP servers silently drop initiation packets whose MAC1 doesn't match a registered key, and MAC1-only probes "always find 0 endpoints" (research §2.3). Every design below follows from that.

The 14 IPv4 /24s are fully enumerated by default (256 addresses each) = 3,584 IPv4 addresses. The two IPv6 /48s are **sampled** (256 addresses each, random tail — warpscout `expandV6`; full /48 enumeration is 2^80 addresses and must never be attempted). IPv6 is off by default (`enable-v6`, §6), so the default plan is IPv4-only; the single default plan-size statement and the v6 arithmetic live in §6.

### 2.2 Sampling and enumeration order

- Per /24: `--sample-per-subnet` (default 256 = the whole /24, §6) selects how many distinct addresses are emitted. A full-period LCG walk per subnet (Hull-Dobell-satisfying parameters, warp-plus `ipscanner/iterator/iterator.go`) covers the full /24 period exactly once, so the walk is deterministic-shuffled, non-repeating, and never materializes the IP list; the planner emits the first N distinct addresses. Subnet visit order is shuffled once per scan.
- /48 v6 pools: `--v6-samples` random addresses per pool (default 256, §6), generated as prefix + random tail, deduplicated.
- Custom CIDR input (opt-in via `--cidr`): core validates every address against `RangePolicy::WarpEndpointPools`, the module's declared policy inside the Cloudflare-owned gate (`01-architecture.md` §6). **`--cidr` accepts IPv4 CIDRs only in v1:** an IPv6 custom CIDR is rejected with the typed range error (`AllowlistViolation`) whose message names that v1 has no custom IPv6 input — the containment rule is written against the superset's IPv4 members, the two IPv6 /48s are sampled-only, and an IPv6 `--cidr` would have no defined interaction with either the per-/24 `sample-per-subnet` walk or the per-/48 `v6-samples`. One rule, over the IPv4 CIDRs v1 accepts: **a custom CIDR must be fully contained in the endpoint-pool superset of §2.1 and have IPv4 prefix length ≥ 20** (warpscout `targetMinBitsV4` = 20). `RangePolicy::PublishedCdn` is **not** accepted here, because only endpoint pools answer handshakes (research §2.1; warp-plus overrides its own `DefaultCFRanges` for the same reason). Accepted: `188.114.96.0/22` (the superset's widest contiguous run) and `162.159.192.0/24`. Rejected: `188.114.96.0/21` (too wide — a /21 is never contained in the superset), a /19, a /16, and any published-CDN CIDR.

## 3. Ports

Units used from here on: an **address** is one plan unit — a network address the module tests; an **endpoint** is `(address, port)`, the probe unit; a **probe** is one endpoint's measurement = 1..=4 **attempts**, and warp's probe makes exactly one; a **finding** is one alive endpoint (§8).

| Mode | Ports | Default |
| --- | --- | --- |
| `pinned` | 2408 only | ✓ |
| `standard` | 500, 1701, 2408, 4500 | |
| `full` | the canonical 54-port list (research §2.2, verified against warp-plus `WarpPorts()`) | |

The canonical list has **54 entries**. Research §2.2's "55/56-port list" heading is a stale label — the list enumerated under it has 54 — and every count, budget and packet charge in this spec assumes 54. `2408` and the standard four are members of it.

The plan carries per-address port lists (`ScanTarget { addr, ports }`) and `stop_on_first_answer`; the runner expands addresses × ports into endpoints. `pinned` emits one port per address and `standard` all four, so `standard` probes each address on four endpoints — four endpoints, hence four probes — and keeps going after an answer: one address answering on 500 and 2408 yields two findings (§8). `full` emits up to 54 ports per address in LCG-shuffled order and sets `stop_on_first_answer`, so once one of an address's endpoints answers the runner skips that address's remaining ports (warpscout's port-discovery strategy, adapted).

The charged count (§6) is the worst case, not a promise: it charges every port of every address, and the packets actually sent are fewer wherever `stop_on_first_answer` truncates an address's port sequence. `--port-mode full` multiplies the endpoint count — and therefore the charge — by 54 over `pinned`; it is opt-in, and §6's invariants reject any full-port plan that exceeds the packet ceiling or cannot finish inside `scan-timeout`.

## 4. The probe (tier 1)

One probe = one WireGuard Noise_IKpsk2 initiation → response/cookie exchange against the registered identity's keys, using **boringtun 0.7.1**'s `noise` module. `Tunn::new(static_private, peer_static_public, preshared_key, keepalive, index, rate_limiter)` builds the tunnel with `preshared_key = None`, `persistent_keepalive = None` and `rate_limiter = None`: WARP carries no PSK, and a non-`None` PSK is a silent trap — the responder cannot derive the same key, so every initiation fails to authenticate and the probe sees silence or at most a cookie reply, never a type-2 response, and the scan reports all-dead with no error to point at. Keepalive is `None` because the probe opens no session, and the limiter is `None` because boringtun then installs its own default peer-handshake limiter, which only the `decapsulate` path this probe never drives would consult. The probe emits the initiation with the direct entry point `Tunn::format_handshake_initiation(dst, force_resend)` (boringtun 0.7.1 rustdoc, `noise::Tunn::format_handshake_initiation`): a 148-byte type-1 message whose MAC1 is keyed with `"mac1----"` + the peer's static public key. `force_resend` is the retry lever **within** an attempt — `false` for the attempt's first send; `true` sends a fresh initiation even when a handshake is already in progress, which is exactly what re-sending after a timed-out attempt needs. `Tunn::encapsulate()` is not this entry point: it emits an initiation only through its no-session fallback path (it queues a payload and then calls the formatter), so a handshake-only probe using it would tie the send to a payload cftool does not have. cftool does not hand-roll the initiation bytes — the library owns the Noise construction, the TAI64N timestamp and MAC1, and cftool supplies the sender index as a `Tunn::new` argument (`index: u32`; not the wire value — §4 step 4). The destination buffer must be at least 148 bytes: the formatter writes the full 148-byte type-1 message, the same "no less than 148 bytes" buffer contract `Tunn::encapsulate` documents as its panic note (boringtun 0.7.1).

Message types are the WireGuard wire format, not this spec's invention: initiation `1` (148 bytes), handshake response `2` (92 bytes), cookie reply `3` (64 bytes). A 92-byte read buffer covers both reply kinds; the type byte decides how many of the read bytes are valid.

Steps per probe — one endpoint (warp-plus `initiateHandshake()` model, research §2.3):

1. **Noise session init** per probe (cheap; keys are static).
2. **Warmup/noise phase** (default `light`; `--noise off` disables the preset's NOISE datagrams only — the warm-up datagram is always sent; presets and overrides in §6): before the initiation the probe sends one warm-up datagram (40–100 bytes, probe-shaped) followed by the preset's noise packets. The warm-up datagram is charged separately in the packet budget as `warmups_per_probe = 1` and is never disabled by `--noise off`; the preset's packets are charged as `noise_datagrams_per_probe` (0 / 5 / 50). The `off` preset therefore charges 2 packets per endpoint (1 attempt + 1 warm-up). Rationale: DPI middleboxes on hostile networks drop cold-burst WireGuard handshakes; this is the community's countermeasure, exposed as a first-class option rather than a hidden trick.
3. **Send initiation:** the 148-byte type-1 message (`0x01`) written by `Tunn::format_handshake_initiation(dst, force_resend)`. v1 sends EXACTLY ONE initiation per probe, so `force_resend` is always `false`; a timed-out attempt ends the probe as `Dead { reason: Timeout }` and is never re-sent, because a re-send would emit a second, uncounted 148-byte datagram and break the 250,000-packet ceiling. (`force_resend = true` is reserved for a future multi-attempt mode.) The local sender index is cftool's choice and has no protocol requirement — cftool picks it and passes it to `Tunn::new(..., index, ...)` (not the wire value — §4 step 4); warp-plus's fixed index 28 is its own choice, and cftool does not need to match it. The TAI64N timestamp and MAC1 (keyed with `"mac1----"` + the responder static public key) are part of the same library output.
4. **Await reply:** read up to 92 bytes with the per-probe timeout and hand them to **`Tunn::parse_incoming_packet(src)`** — boringtun 0.7.1's response-side entry point, the counterpart of the initiation formatter — which yields `Packet::HandshakeResponse` for a type-2 message or `Packet::PacketCookieReply` for a type-3 one. `parse_incoming_packet` is **parse-only** — it reads the layout and performs **no** cryptographic check. The public verifying path is **`Tunn::decapsulate(src_addr: Option<IpAddr>, src: &[u8], dst: &mut [u8]) -> TunnResult`** — the only public route to the handshake's `receive_handshake_response`, where the AEAD open happens; `handle_verified_packet` is crate-private and not reachable from cftool. This probe does **not** drive `decapsulate`, so it classifies with `parse_incoming_packet` and must not claim to have decrypted anything. The type byte and length decide the outcome:
   - **Type 2 (`0x02`) handshake response, exactly 92 bytes:** sender index = bytes 4..8 (the responder's own index), receiver index = bytes 8..12 (**our** index, echoed back), encrypted ephemeral = bytes 12..44, encrypted nothing = bytes 44..60, MAC1 = bytes 60..76 and MAC2 = bytes 76..92 (the two MACs occupy the 32-byte region 60..92). The probe **MUST** check that the **receiver** index equals the sender index the initiation carried in bytes 4..8 — the sole comparison source is those 4 bytes of the initiation the probe itself sent, which it knows exactly — because the responder echoes the initiator's index there; the sender index belongs to the responder and is **not** compared. The `index` argument passed to `Tunn::new` is **not** that wire value: boringtun transforms it (stores `index << 8`, then increments the low byte before the first send), so the first initiation's bytes 4..8 carry `(index << 8) + 1`; comparing a response against the constructor argument mismatches on every endpoint and classifies the whole scan `Dead { reason: DeadReason::ParseFailure }` with no error to point at. Acceptance rule: **92 bytes, type 2, receiver index == ours** → `Alive { rtt: Some(handshake_rtt), detail: AliveDetail { kind: AliveKind::Type2Response, facts: {} } }`, RTT = initiation-send → valid-response time. A reply that fails the length, type or receiver-index check is not ours: `Dead { reason: DeadReason::ParseFailure }`, never alive. What a type-2 response **does** prove is the responder's static key: the server decrypts the initiation's encrypted_static only after validating MAC1 against that key, and it answers with a type-2 response — rather than a cookie or silence — only when that succeeded.
   - **Type 3 (`0x03`) cookie reply, exactly 64 bytes:** the endpoint is up and rate-limiting us → `Alive { rtt: None, detail: AliveDetail { kind: AliveKind::Cookie, facts: {} } }`; surfaced in output, unranked (§8). A cookie reply proves only that the endpoint answered — never the responder's static key — and it carries no handshake timing.
5. **Outcome and attempt record.** The probe returns the shared `ProbeOutcome { target, verdict, attempts: AttemptRecord, started_at }`, whose `AttemptRecord { tries_made, tries_succeeded, try_rtts_us }` (`01-architecture.md` §3.2) carries its per-attempt results. warp's values: one try per probe, so `tries_made = 1`; `tries_succeeded` is 1 when that try produced an answer (a type-2 response or a type-3 cookie reply) and 0 otherwise, and `try_rtts_us` holds the handshake RTT for a type-2 try — a cookie reply is alive but carries no handshake timing. Those counts feed loss and mean-RTT only: **liveness is the verdict**, and a probe is alive iff `verdict` is `Alive` — never derived from `tries_succeeded`. The verdict mapping is exactly: a type-2 response → `Alive { rtt: Some(handshake_rtt), detail: AliveDetail { kind: AliveKind::Type2Response, facts: {} } }`; a type-3 cookie reply → `Alive { rtt: None, detail: AliveDetail { kind: AliveKind::Cookie, facts: {} } }` (alive, no timing, unranked, §8); a timeout, an unreachable endpoint or a parse failure → `Dead { reason: DeadReason::Timeout | Unreachable | ParseFailure }`. A probe cancelled mid-flight is `Dead { reason: DeadReason::Cancelled }` even if an earlier try had succeeded — the cancellation wins — and it is counted dead, never a finding (the token travels in `ProbeBudget`, `01-architecture.md` §5). warp has no `Filtered` verdict: filtering is the post-probe `max-rtt`/top-N step, marked on a finding by `is_filtered()` (§8).

**Responder static key.** MAC1 is keyed with `"mac1----"` + the responder's static public key. For WARP that key is the WARP peer key returned by the registration/device-config response (`config.peers[].public_key`), alongside the endpoint the identity uses (`config.peers[].endpoint`) — the same two fields wgcf's profile generator reads (`cmd/generate/generate.go:54`). It is server-issued and may rotate, so it is stored in the identity file (§5) with the rest of the registration response — never compiled in. The value commonly seen in older wgcf-generated profiles and third-party configs is a historical constant: it MUST be re-verified against a live registration before use and must not be hardcoded on trust. A stale or wrong key yields silence or cookie replies only, never a type-2 response; T4 is the live check.

### 4.1 Why per-probe handshake state is safe

Each probe builds its own ephemeral handshake state from the static identity keys; no cross-probe state is shared, so bounded concurrency cannot corrupt sessions. The identity itself is process-level state (§5).

## 5. Identity bootstrap

Probes need a registered WARP identity (Curve25519 keypair + the registration Cloudflare's API returns when the official client registers). cftool v1:

**Registration contract** (verified against ViRb3/wgcf master, 2026-11-16; TLS evidence in `docs/research/warp-registration-tls.md`; isolated in one function — `06-qa.md` risk (e)):

| Item | Value |
| --- | --- |
| Method + path | `POST https://api.cloudflareclient.com/v0a5641/reg` |
| Headers | `User-Agent: 1.1.1.1/6.38.9-5641 (Android 16.0.0)`, `CF-Client-Version: a-6.38.9-5641`, `Content-Type: application/json; charset=UTF-8`, `Connection: Keep-Alive`, and no `Accept` header — sent verbatim, as upstream does |
| TLS profile | TLS 1.2 pinned as both minimum and maximum; HTTP/1.1 only, ALPN `http/1.1`; cipher suites exactly `TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384` (0xC02C) and `TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384` (0xC030) |
| Response fields used | `config.peers[].public_key` (responder static key, §4), `config.peers[].endpoint`, and `config.client_id` (base64; its 3 decoded bytes are WARP's `reserved` client id) — read from the response, never assumed; the P1 spike re-confirms this field path against a live 2xx body |
| Body (JSON) | Exactly these fields: `fcm_token: ""`, `install_id: ""` (both populated by Firebase in the Android app), `key` (the Curve25519 public key, standard base64 — Key encoding row), `locale: "en_US"`, `model` (device model string), `tos` (registration timestamp), `serial_number: ""` (required by the API), `os_version: "16.0.0"`, `key_type: "curve25519"`, `tunnel_type: "wireguard"`. No other field is sent. |
| Key encoding | The 32-byte Curve25519 public key in standard base64, padded — the same encoding WireGuard configs use |

The body is wgcf master's `RegisterRequest` (`cloudflare/api.go:235-252`; `openapi/model_register_request.go`, generated for the WARP Android API contract of version 6.38.9, build 5641). Its required fields are `fcm_token`, `install_id`, `key`, `locale` and `serial_number`; the remaining five above are optional in the model and sent with the fixed values shown.

- **One build constant.** The URL version segment (`v0a5641`), the `User-Agent` (`1.1.1.1/6.38.9-5641 (Android 16.0.0)`) and `CF-Client-Version` (`a-6.38.9-5641`) all carry the same build number (`5641`); derive all three from one constant so a version bump cannot leave them inconsistent. The values above were re-verified against ViRb3/wgcf master on 2026-11-16 (`cloudflare/api.go:25,31,32`); research §2.7's `v0a884`/`okhttp` pair is outdated and is cited for the technique only.
- **API version is a moving target.** `v0a5641` is the verified value at spec time. The version segment is a config value (default `v0a5641`) derived from the single build constant above; a **404** reports `RegistrationRejected { status, api_version }` with the "Cloudflare may have changed the API version" hint, never a generic transport error. Re-verify the default at build time.
- **TLS profile — verified; whether it is *required* is not.** The profile the registration presents is known and fixed: TLS 1.2 pinned as both minimum and maximum, exactly the two AES-256-GCM suites `TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384` (0xC02C) and `TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384` (0xC030), ALPN `http/1.1`, HTTP/1.1 only (wgcf master; `docs/research/warp-registration-tls.md` §1, §4). Whether a **stock** Rust ClientHello is refused is **unverified**: wgcf's Go client used stock `crypto/tls` for years and registered successfully, and the September 2026 failures were **429**s whose cause was never isolated — the fix changed API version, headers and TLS in one commit (`warp-registration-tls.md` §2). This spec therefore does not assert that a stock hello will be refused.
- **Strategy — simplest stack first, and the primary path must clear the toolchain floor.** The P1 spike (`06-qa.md` risk (e); `warp-registration-tls.md` §5) tries `reqwest` 0.13.5 + `rustls` with TLS 1.2 pinned through the non-deprecated builder methods `tls_version_min(tls::Version::TLS_1_2)` / `tls_version_max(tls::Version::TLS_1_2)` — the `min_tls_version` / `max_tls_version` spellings in `warp-registration-tls.md` §5 are `#[deprecated]` on 0.13.5 and would fail the workspace's `clippy -- -D warnings` gate — `.http1_only()`, and `tls_backend_preconfigured` to inject a rustls `ClientConfig` whose provider carries only the two suites above and whose `alpn_protocols` is `[b"http/1.1"]`. The fallback, paid for only if the spike fails, is a ClientHello-impersonating client — `wreq` 0.16.3 on BoringSSL with a `TlsOptions` that also fixes extension order, curves, sigalgs and GREASE — behind the **same** `register()` seam, so the swap is one module and no caller changes. The fallback is not available everywhere the primary path is: `wreq` 0.16.3 declares MSRV 1.98, above this workspace's Rust floor, so it exists only on a newer toolchain — the primary path must succeed on the floor, and raising the floor for the fallback is a separate decision, not a spike outcome.
- **Status mapping — one pure function, which is the test seam.** `RegistrationRejected { status, api_version }` is the single error variant for a non-2xx registration, and every status→hint decision is made by the pure function `registration_rejected(status: u16, api_version: &str) -> RegistrationRejected` — it returns `RegistrationRejected { status, api_version }` and selects the hint text from the status and version alone, touching no transport, clock or identity state, so T6 calls it directly and no HTTP seam is needed; that a live server actually returns these statuses is proved only by the P1 spike (risk (e), `06-qa.md`). `status` has three meanings: **404** → API version drift (the build constant is stale; the hint says Cloudflare may have changed the API version); **403** (observed as Cloudflare error `1020`) → fingerprint/policy rejection (the hint names the TLS profile, phrased "likely" until the spike confirms the hypothesis); **429** → rate-limited (the hint says try again later, and registration is never retried in a loop). The 403/`1020` reading is a **hypothesis, not a documented fact**: it comes from wgcf 2.2.32's historical code comment ("Match app's TLS config or API will reject us with code 403 error 1020"), and the rejection actually reproduced in 2026 was a **429** (wgcf issue #626) — no 403/`1020` was observed. The P1 spike must confirm the fingerprint diagnosis; until it does, the 403 error text says "likely fingerprint/policy rejection" rather than asserting it, and a 429 is never evidence of a fingerprint mismatch (`docs/research/warp-registration-tls.md` §6–§7). Any other non-2xx carries its status under the same variant, distinct from a transport failure.
- **No identity, no scan — and the gate runs last.** With no registered identity, `plan()` returns `ScanError::IdentityMissing` before any address is generated or socket opened; the CLI prints the remedy `cftool warp identity register`; the GUI shows the same remedy with a "Register identity…" action. The module never auto-registers silently — registration is always one explicit user action. The identity check is the **last** step of `plan()`, in the order options → range → budget → identity: option validation (`OptionsInvalid`), then range-policy validation (`AllowlistViolation`, §2.2), then the plan/budget checks (`InvalidPlan`, §6), then the gate — `01-architecture.md` §3's validation order plus the identity gate. That ordering is load-bearing: `cftool warp-scan --cidr 192.0.2.0/31` must fail on the allowlist (`04-cli.md` §8 T2) even on a machine that has never registered, not report `IdentityMissing`, and a plan that breaches the packet ceiling reports `InvalidPlan` whatever the identity state.
- **Mock identity and scripted probes (tests).** The scripted identity is **warp's, not core's**: `cftool-warp` provides it — its `mock` cargo feature enables the scripted-identity loader — because the identity artifact and the `IdentityMissing` gate belong to this module, while `cftool-core` supplies only the scripted probe source. The loader needs no network, so the identity gate is satisfied under `--mock` and tests run with `--features mock`; `04-cli.md` §8 T2/T3 and `05-gui.md` §7 G5 are executable hermetically on a machine that has never registered. A supplied probe script **replaces the plan's target set** — the script's targets are what runs, not §2.1's addresses — so `totals.probed` equals the script's target count.
- **Storage:** `identity.json` under the config dir (0600 on unix; user-profile ACL on Windows). Fields: private key, the WARP peer public key and endpoint from the registration response (`config.peers[]`, §4), and the reserved bytes — the 3 decoded bytes of `config.client_id`, recorded for tier 2's data plane (§7) and not needed by handshake-only probes.
- **Import — the recovery path when registration is refused.** `cftool warp identity import <file>` reads a WGCF-format config — private key, peer public key, endpoint, reserved bytes — and writes it to `identity.json`, with no network call. An identity generated elsewhere therefore still scans when registration is refused (429, `1020`, or API drift, above). Import only — there is no export (Vision N2) — and the GUI's identity dialog offers the same action beside `Register identity…` (`05-gui.md` §3.3).
- **Commands and dialog are declared, never named by a frontend.** The module declares `identity register` (with `--force` in its declared args), `identity import` (with the file path in its declared args), `identity show` (no declared args) and the `identity` dialog through the shared metadata — `SubcommandSpec { name, args: &'static [OptionSpec], .. }` consumed by the trait's `run_command(id, args, cancel)`, and `DialogSpec { id, title, fields, confirm_command }` (`01-architecture.md` §5) — so both frontends dispatch on the declared id/name alone, neither frontend names this module's command or dialog surface, and Vision S4's four-edit removal still compiles both frontends.
- Freshness: identities don't expire for scanning purposes; `--force` re-registers; failures surface the HTTP status and the mapping above.
- **Ethical note (Vision P4):** this is the same registration the official client performs, with a legitimately generated keypair — the same packets the official app sends, to endpoints Cloudflare publishes for client use. No automation beyond one registration per user action. The tool carries the community's non-affiliation + ToS notice in `--help` and the GUI About dialog.

| Preset | Count | Packet size | Spacing | Source |
| --- | --- | --- | --- | --- |
| `light` | 5 | 50–100 bytes | 1–5 ms | BPB-Warp-Scanner profile (research §2.3) |
| `heavy` | 20–50 | 40–100 bytes | 80–150 ms | warp-plus `initiateHandshake()` (research §2.3) |

**Default plan.** One statement for the whole spec: with all defaults and `enable-v6` off, the plan is 14 × 256 = **3,584 IPv4 addresses** on one pinned port → **3,584 endpoints** (3,584 probes, `charged_packet_count` = 3,584 × (1 + 1 + 5) = **25,088 packets**). Enabling IPv6 adds 2 × 256 = 512 sampled addresses → **4,096 addresses / 4,096 endpoints / 28,672 charged packets**. §2.1 and §9 T5 use this plan.

**`results` and `max-rtt` never shorten the plan.** The scan always runs the full plan — predictable duration, matching the 90 s ceiling — and `results` is the number of findings retained (top-N by `sort_rank`). warp-plus stops early once its queue fills; cftool deliberately does not (research §2.4). `max-rtt` is a finding filter: an RTT-ranked endpoint above 400 ms is not retained and the scan still completes. Cookie-challenged findings carry no RTT; they are kept in addition to `results`, outside the RTT ranking (§4, §8).

**Invariants** (validated at plan time; violation = `ScanError::InvalidPlan`, nothing probed — except `concurrency`'s ceiling split, whose core half is a runner-construction backstop, below):

- `charged_packet_count` = endpoints × (`attempts_per_probe` + `warmups_per_probe` + `noise_datagrams_per_probe`) — one field, one formula (`01-architecture.md` §5). The runner expands the plan's `ScanTarget { addr, ports }` lists into endpoints (§3); warp's probe makes 1 attempt — one initiation, never re-sent (§4 step 3) — and charges 1 warm-up, and `noise_datagrams_per_probe` is the preset's datagram count (0 `off`, 5 `light`, 50 `heavy` at worst) — a per-probe charge of 2 / 7 / 52. Because v1 never re-sends, every datagram the probe emits is inside that charge. `pinned`/`light` = 3,584 × (1 + 1 + 5) = **25,088 packets**; `pinned`/`heavy` = 3,584 × (1 + 1 + 50) = **186,368**; `full`/`heavy` = 3,584 × 54 × 52 = **10,063,872**. The field is carried in the plan, never recomputed by consumers.
- `charged_packet_count` ≤ 250,000 packets per scan (`01-architecture.md` §9; Vision §3.1). The ceiling counts datagrams, not measurements, and that is what bounds `full` at the default address count: 3,584 addresses × 54 ports = 193,536 endpoints charge 193,536 × (1 + 1) = **387,072** packets even with `--noise off`, **1,354,752** at the default `light` and **10,063,872** at `heavy` — `InvalidPlan` naming the count and the ceiling. A smaller plan fits both invariants: `--cidr 188.114.96.0/24` is 256 addresses → 256 × 54 = 13,824 endpoints → 13,824 × 7 = **96,768** packets at `full`/`light`, inside the 250,000 ceiling, and its floor is 1 address-wave (256 addresses, all inside the 512 concurrency) × 54 ports × 1.525 s ≈ **82 s**, inside 90 s.
- `plan_endpoints` ≤ 64,512 endpoints (65,536 result-lane events minus the 1,024-event control/log allowance, `01-architecture.md` §9). The result lane carries one `Result` per endpoint plus the `Started`, `Phase`, `Log` and `Done` control events, and a full lane aborts the scan with `ScanError::ResultLaneOverflow` (exit 6, `01-architecture.md` §3.1), so a plan above 64,512 is `ScanError::InvalidPlan` (exit 3) whose message names the computed endpoint count, the 64,512 bound and the 1,024-event allowance; `ResultLaneOverflow` stays the runtime backstop for a count that slipped past `plan()`, never the intended path for a plan the bound can refuse. A plan at exactly 65,536 endpoints is already over the line before the scan emits its first `Log`. This bound is independent of the packet ceiling and the timeout floor: `--sample-per-subnet 100 --port-mode full --noise off --scan-timeout 300` is 14 × 100 = 1,400 addresses × 54 ports = **75,600 endpoints** — 75,600 × (1 + 1 + 0) = **151,200 charged packets** (inside 250,000) and a floor of ceil(1,400 / 512) = 3 address-waves × 54 ports × 1.5 s = **243 s** (inside 300 s), so every other invariant passes and only this one rejects it; left unvalidated it would stream ~75.6k `Result` events into the 65,536-event lane and abort mid-scan.
- `scan-timeout` ≥ ceil(`addresses` / `concurrency`) × `ports-per-address` × `per_probe_timeout`, where `per_probe_timeout` is the probe's total cap in the probe time model (`01-architecture.md` §5): `overhead + max_attempts × per_attempt_timeout`. warp's probe makes exactly one attempt, so its `overhead` is the noise preset's delay and `per_probe_timeout` = noise delay + 1 × `timeout-per-probe` (default 1.5 s): `off` 1.5 s, `light` ≈ 1.525 s (25 ms + 1.5 s), `heavy` 9 s (7.5 s + 1.5 s). The floor is **per address**, which is a conservative upper bound on the scan's wall-clock; concurrency itself is measured in ENDPOINTS (a permit per in-flight endpoint, `01-architecture.md` §3), so one address's several ports are NOT serialized behind a single permit — `stop_on_first_answer` is checked before dispatching an address's remaining ports, so a multi-port address never exceeds its share of the ≤ 512 in-flight endpoints. `full`'s port sequence stops at the first answer (§3), so the charged count is a deliberate worst case — and that worst case is why `full` at defaults is infeasible: ceil(3,584 / 512) = 7 address-waves × 54 ports × 1.525 s ≈ **576 s** (378 endpoint-waves) > 90 s, a second, independent rejection on top of the packet ceiling above: the floor alone needs ≈576 s, and even a `scan-timeout` raised past it leaves the plan rejected by the ceiling. The error names the violated numbers and, for the floor, the minimum `scan-timeout`.
- `concurrency` ∈ 1..=4096, one owner per ceiling: the MODULE owns its declared ceiling through option validation — warp declares 4,096, so `plan()`'s option step rejects a value above 4,096 as `ScanError::OptionsInvalid` (exit 1), never `InvalidPlan` — and CORE's 4,096 is a runner-construction BACKSTOP returning `ScanError::InvalidPlan` (exit 3) before any probe opens (`01-architecture.md` §5, §9), not a plan-time concurrency check. A warp value above 4,096 therefore never reaches core's backstop, which exists for any module that declares a ceiling above 4,096 or omits one.
- `v6-samples` ≥ 64 when `enable-v6` (protects RTT stats).
- `noise = heavy` charges up to 50 datagrams **and** up to `count-max` × `delay-max` = 50 × 150 ms = 7.5 s of delay per probe — one preset, two costs, so the packet charge and the floor agree. In the probe time model the per-probe cost becomes `per_probe_timeout` = 7.5 s overhead + 1 × 1.5 s = 9 s, and the packet term 52: `pinned`/`heavy` needs 7 address-waves × 1 port × 9 s = 63 s and 186,368 packets — inside both ceilings; `standard`/`heavy` needs 7 × 4 × 9 s = 252 s and 745,472 packets — rejected on both. `light` charges 5 datagrams and adds ≤ 25 ms (5 × 5 ms): `per_probe_timeout` ≈ 1.525 s, so `pinned`/`light` is 7 × 1 × 1.525 s ≈ **10.7 s**, still far inside 90 s — the delay is small but it is counted, never rounded away.

**Timing.** Defaults (3,584 endpoints, 512 concurrency, `per_probe_timeout` ≈ 1.525 s): the worst case is bounded by ≈ 10.7 s (7 address-waves × the 1.525 s per-probe cap); the typical case is far lower, since a probe that answers quickly never consumes its full cap. The 90 s `scan-timeout` remains the hard ceiling — Vision S2 with headroom.

## 7. Tier 2: in-tunnel validation (post-v1, not in v1)

**Status: post-v1 (not in v1).** Nothing in this section ships in v1. It is the full design for a later release, carried here so the tier-1 output model accommodates it (the `colo`/`exit_country` columns, §8) and so the spike has a target. It enters a release only after a named spike exits — wintun availability and elevation on Windows, tunnel bring-up, in-tunnel ping, and the colo/country fetch proven end to end — **and** behind its own cargo feature gate, so a plain build carries no TUN driver, no elevation path and no in-tunnel HTTP client. The phase reports `Tier2Outcome { Skipped { reason }, Completed, Failed { reason } }`; a skip surfaces as one `ScanEvent::Log` plus the finding rows (tier-2 fields stay `null`) and leaves the tier-1 findings otherwise unchanged.

Handshake-alive ≠ usable on filtered networks (warpscout's core lesson; UMBRA v3.8: "a TCP connect was never proof of an endpoint"). Tier 2 runs *after* tier-1 ranking, only on the top `results` endpoints:

1. **Precondition — tunnel availability.** A userspace WireGuard tunnel on Windows needs a TUN driver (wintun) and an elevated process. Note that boringtun 0.7.1's `device` module is unix-only — it ships no Windows TUN path — so the Windows tunnel is additional integration work the tier-2 spike must prove, not something the library provides. The module checks TUN availability and elevation before the phase starts. If either is missing, tier 2 is **skipped** (`Tier2Outcome::Skipped { reason }`) with an explicit `Log` event ("tier 2 skipped: wintun/elevation required") and the tier-1 findings stand unchanged — a missing privilege never fails the scan.
2. **Tunnel bring-up:** boringtun userspace tunnel to the candidate endpoint with the registered identity (including its stored `reserved` bytes, which WARP's data plane requires), MTU 1280 — the value Cloudflare's own client ships (wgcf's profile template sets `MTU = 1280`; 1420 is WireGuard's generic IPv4 default and is not what WARP profiles use; re-verify at build time). Allowed IPs are the measurement scope only: `1.1.1.1/32` plus the v4 /32s of `speed.cloudflare.com`, resolved by the system resolver *before* the tunnel starts and pinned into the HTTP client for the meta fetch. The tunnel is a measurement harness with single-destination routing, not a general data path (Vision N1); every other destination bypasses it.
3. **In-tunnel ping:** `1.1.1.1` with a 10-echo burst; compute loss + RTT.
4. **Tail-loss check:** an endpoint whose burst shows ≥3 consecutive losses at the tail is flagged `torn-down` (DPI kill signature, warpscout's method) and demoted by the §8 rank rule, never by an RTT multiplier: it stays ranked, and `sort_rank = (1 << 32) | rtt_us` puts it after every non-flagged endpoint regardless of RTT, while its own RTT still orders the flagged ones among themselves.
5. **Meta fetch:** `GET https://speed.cloudflare.com/meta` in-tunnel, with the client pinned to the step-2 addresses (the `resolve()` pinning pattern of `03-cdn-scan.md` §3.1) so a re-resolution cannot pick an IP outside the tunnel's allowed set. Records exit country + colo (IATA) in the finding (`exit_country`, `colo`; warpscout's report model).
6. **Concurrency:** max 10 tunnels concurrently (warpscout `-jt 10`); each tunnel is fully torn down after validation (≤ 15 s cap).
7. **Cancellation-aware teardown:** when the scan's cancellation token fires, in-flight tunnels are torn down promptly — not waited out to the 15 s cap. Teardown removes the tunnel's TUN interface and closes its sockets; it completes within 1 s so the engine task can be joined inside the GUI's 2 s window-close bound (`05-gui.md` §4). A tunnel that cannot be torn down in that time is reported as one `ScanEvent::Log` (`teardown-timeout: <endpoint>`) rather than silently leaked — the `ScanSummary` has no field for it, and a log line keeps the leak visible without inventing a counter.

**Release gate.** Tier 2 enters a release only when the spike above has exited and its cargo feature is enabled; in such a build `--validate` turns the phase on, and it is still OFF by default. Whether it becomes default-on is qmahyar's call at build time, not a spec commitment. Anything beyond this measurement harness stays post-v1.

## 8. Output findings

Per-endpoint finding (implements arch §4 `ModuleFinding`). The module declares its result columns with `fn columns(&self) -> &[ColumnSpec]` (arch §5), `ColumnSpec { key, header }`; the CLI table and CSV render exactly those columns in declared order, and each finding's `to_row()` emits exactly those keys (arch §4). `FindingRow` carries the declared keys and nothing else — there is no auxiliary map, and an inapplicable field is `CellValue::Null`. The keys are defined once here and inherited by the table, CSV and JSON:

| Key | Header | Value |
| --- | --- | --- |
| `endpoint` | Endpoint (`ip:port`) | the finding's endpoint — `address:port`, one row per alive endpoint whatever the address's port count (§3) |
| `rtt_ms` | RTT (ms) | handshake RTT from a type-2 response (`AliveKind::Type2Response`); null for a cookie finding (`AliveKind::Cookie`) |
| `status` | Status | `alive` / `cookie` / `torn-down` (`alive` = type-2 response, `cookie` = type-3 cookie reply; `torn-down` is tier-2 only, §7) |
| `colo` | Colo | tier-2 exit colo (IATA); null when tier 2 is off (always, in v1) |
| `exit_country` | Exit country | tier-2 exit country; null when tier 2 is off (always, in v1) |
| `noise_preset` | Noise preset | preset used (`off` / `light` / `heavy`) |

- **Ranking — `sort_rank(&self) -> Option<u64>`.** A single `u64` in microseconds; `Some(rank)` sorts ascending (lower is better) and core orders the `finalize` output by it. An `AliveKind::Type2Response` finding ranks by its measured handshake RTT, `sort_rank = rtt_us`. A `torn-down` endpoint (§7 step 4) stays ranked but is demoted unconditionally by a flag bit: `sort_rank = (1 << 32) | rtt_us`, so every torn-down endpoint sorts after every non-flagged endpoint regardless of RTT, while its own RTT still orders the flagged ones among themselves. (The high bit is set only for flagged endpoints; `rtt_us` fits in the low 32 bits.) A cookie finding (`AliveKind::Cookie`, `rtt: None`) carries no RTT and therefore returns `None`: it is unranked, listed after every ranked finding, and never dropped from the output — `None` never means "omit this finding" (arch §4).
- **`results` counts ranked findings only.** The top-N applies to ranked findings; an unranked cookie finding never occupies one of the `results` slots — it is always listed, in addition to the top-N, never inside it (§6).
- **One finding per alive endpoint — never per address.** warp's `finalize` emits a finding when the verdict is `Alive` — `AliveKind::Type2Response` or `AliveKind::Cookie` (§4). An address that answers on two ports yields two findings, one per endpoint; `alive` counts endpoints, so `alive` equals the number of findings. An endpoint whose verdict is `Dead` — including a probe cancelled mid-flight, even after an answered try — produces no row at all: `probed` counts endpoints attempted, `dead = probed − alive` is never serialized and never a row (`01-architecture.md` §4), and `filtered` stays a subset of `alive`.
- **Drops are marked by `is_filtered()`, not by a status string.** An endpoint the `max-rtt` filter drops or the retained top-N cuts keeps its finding and reports `is_filtered() == true`; "not retained" (§6) means not retained in the ranked set, never removed from the findings. The `status` column carries only `alive` / `cookie` / `torn-down` and does not encode filtering.
- **`totals.filtered`.** warp's `totals.filtered` = the number of findings marked `is_filtered()` — alive endpoints the `max-rtt` filter dropped or the retained top-N cut. It is a subset of `alive`, never a separate probe verdict class, and `dead` endpoints never appear in it. Cookie-challenged findings are alive and always retained, so they are never counted there.
- CSV header/row per arch §4 (headers come from `columns()` in declared order, never from the finding type); JSON serializes the same row, so tier-2 fields appear as `null` when tier 2 is off — there is no flatten/`extra` map.
- Live progress shows the same four fields in both frontends: completed/total, `alive`, elapsed, and the current top-5 endpoints by RTT — the CLI renders them as its status line (`04-cli.md` §3).

## 9. Success tests (module level)

- T1: unit — LCG walk over a /24 emits all 256 addresses exactly once before repeating (full-period property test).
- T2: unit — plan validation (§2.2, one IPv4 rule — containment in the endpoint-pool superset **and** prefix ≥ /20 — plus the IPv4-only input rule), run in the order options → range → budget → identity (§5): a published-CDN CIDR (inside the global allowlist, outside the §2.1 endpoint superset), `188.114.96.0/21` (too wide — a /21 is never contained in the pool superset) and a /19 are each rejected as `AllowlistViolation`; a /16 is the same typed error; `188.114.96.0/22` → accepted; `162.159.192.0/24` → accepted; an IPv6 CIDR (`2606:4700:d0::/48`, inside the superset) → `AllowlistViolation` naming that v1 takes no custom IPv6 input; `v6-samples` < 64 with v6 enabled → typed error. The identity gate remains last: with no identity on disk those allowlist cases still return `AllowlistViolation`, not `IdentityMissing`, and a valid CIDR reaches the gate (`IdentityMissing`).
- T3: unit — plan invariants (§6): `port-mode full` at defaults is rejected (`InvalidPlan`; it breaches both the packet ceiling and the ≈576 s floor); `charged_packet_count` > 250,000 → typed plan error; the default plan passes; `noise = heavy` requires the 63 s floor (a 60 s `scan-timeout` is rejected); totals on a synthetic `standard`-mode scan in which two endpoints of one address answer: `alive` = 2, the findings vector holds two rows (one per endpoint), and `probed = alive + dead` holds; a synthetic plan above 64,512 endpoints — 75,600, from `--sample-per-subnet 100 --port-mode full --noise off --scan-timeout 300`, which passes the packet ceiling at 151,200 charged packets and the 243 s floor — returns `ScanError::InvalidPlan` naming the 75,600 endpoint count and the 64,512 bound, with no probe started.
- T4: `#[ignore]` live — handshake probe against `engage.cloudflareclient.com:2408` from a registered identity must produce a **type-2 (`0x02`) handshake response**: exactly 92 bytes, with the **receiver** index at bytes 8..12 equal to the sender index the initiation carried at bytes 4..8 — taken from the initiation bytes the probe sent, never from the `index` argument passed to `Tunn::new`, which boringtun transforms (`index << 8`, then an increment before the first send, so the wire value is `(index << 8) + 1`) — and the verdict `Alive { rtt: Some(..), detail: AliveDetail { kind: AliveKind::Type2Response, facts: {} } }` with RTT < 400 ms. The assertion is the **receiver-index check, not a payload decryption**: `Tunn::parse_incoming_packet` parses the layout only, and the AEAD open lives in `receive_handshake_response`, reachable only through `Tunn::decapsulate`, which this probe does not drive. A type-2 response is the only reply that proves the responder's static key (§4 step 4); `≥ 1 Alive` is not the assertion: a type-3 cookie reply is also `Alive` (`rtt: None`, `detail: AliveDetail { kind: AliveKind::Cookie, .. }`) and proves only that the endpoint answered, not that our MAC1 key is the responder's. A cookie reply from the same probe is a separate, weaker assertion (`AliveKind::Cookie`, no RTT, unranked §8) — reachability, never proof of the responder key.
- T5: `#[ignore]` live — full default scan completes < 90 s and produces ≥ 1 finding on a healthy network.
- T6: unit — identity gate ordering and registration mapping (§5): no identity file with default options → `plan()` returns `IdentityMissing` before address generation; the same with `--cidr 192.0.2.0/31` → the allowlist error, not `IdentityMissing` (the gate runs last); the status→hint mapping is asserted by calling the pure `registration_rejected(status, api_version)` directly — 404 → `RegistrationRejected` with the version-drift hint; 403 (the `1020` signature) → the fingerprint text; 429 → the rate-limit hint, with no retry — because the `mock` feature loads a scripted identity, not a registration HTTP response, so there is no seam for a synthetic HTTP status. The live transport is proved only by the P1 spike (risk (e)), so this case runs hermetically in gate 4 (`cargo test --workspace`, no `--features mock`).
- T7 (**post-v1 test**, not a v1 gate; gated with §7): unit — tier 2 with tunnel availability forced off returns `Tier2Outcome::Skipped { reason }`, emits one `ScanEvent::Log`, and leaves the tier-1 findings unchanged with the tier-2 fields `null`.
- T8: unit — finalize folding (§8): over synthetic outcomes, the findings come out in rank order — healthy endpoints by ascending RTT; a torn-down endpoint sorts after every non-flagged endpoint because of the `(1 << 32) | rtt_us` rank bit; cookie-challenged findings are unranked and listed last. `max-rtt` drops and top-N cuts are marked `is_filtered() == true`; cookie findings never occupy a `results` slot and are never counted in `totals.filtered`; `totals.filtered` equals the number of findings marked filtered.
- T9: unit — identity import (§5): a WGCF-format fixture (private key, peer public key, endpoint, reserved bytes) is parsed and stored in `identity.json` with all four fields; a malformed fixture is a typed error naming the missing or invalid field, and nothing is written on failure.
