# cftool — cdn-scan Module Spec

- Status: Draft v1 (spec phase)
- Date: 2026-11-16
- Depends on: `00-vision.md`, `01-architecture.md`
- Evidence base: `docs/research/scanner-landscape.md` §2.1, §2.5, §2.6, §4-§5 (CFST methodology, source-verified)

## 1. Purpose

`cdn-scan` measures latency (and optionally throughput) of Cloudflare CDN edge IPs over Cloudflare's published ranges, so a user can pick the fastest healthy edge for their network — the CloudflareSpeedTest (CFST) methodology, rebuilt on cftool's engine.

## 2. Target model

### 2.1 Ranges

Source of truth: Cloudflare's published lists — `https://www.cloudflare.com/ips-v4` (15 CIDRs) and `https://www.cloudflare.com/ips-v6` (7 CIDRs). Fetched by `core::ranges::RangeSource` (arch §6): bundled snapshot compiled in (from the current published lists at spec time), refreshed over HTTP with 24 h cache, offline fallback to snapshot with a Log event.

### 2.2 Sampling

- **IPv4 (default):** one random address per /24 within each published v4 CIDR (CFST default) — 5,956 targets on the spec-time list. `--sample-per-subnet N` draws N per /24, deduplicated within the /24 (Vision S5 raises this until the planner reports ≥ 10,000).
- **IPv6 (opt-in):** `--v6` adds N random addresses per published v6 CIDR, `--v6-samples` default 16, built as CIDR prefix + uniformly random tail bits and deduplicated across the plan. Sampling is bounded per published CIDR, not per /64: published v6 CIDRs are far larger than /64, so a per-/64 rule is not computable. v6 is off in the default profile unless `--v6` is passed; `--v6-samples` has no effect without it (7 CIDRs × 16 = 112 targets at defaults).
- **`--all-ips`:** full per-address enumeration of the published v4 ranges (CFST `-allip`) — 1,524,736 targets on the spec-time list. Allowed only when the resulting plan stays within the packet ceiling (250,000 charged packets per scan, `01-architecture.md` §9) and the result-lane capacity (65,536 events, of which 1,024 are reserved for control and log events, so at most 64,512 endpoints — `01-architecture.md` §3.1). tcp mode charges 5 packets per target, so that ceiling admits at most 50,000 targets; the endpoint count must also stay ≤ 64,512, which binds http mode (2 packets each: 64,512 × 2 = 129,024, inside 250,000). A larger plan returns `ScanError::InvalidPlan` (arch §8) whose message names the computed charged-packet count (7,623,680 for this plan), the 250,000-packet ceiling, `--all-ips` as the cause, AND the remedy that actually runs: `--sample-per-subnet 2 --scan-timeout 300` — 11,912 addresses sit inside the packet ceiling, but their latency floor is ceil(11,912 / 200) × 5 s = **300 s**, above the 180 s default, so naming `--sample-per-subnet` without the ceiling would only produce a second `InvalidPlan`. The count is computed from CIDR arithmetic before any target is materialized (T2). There is no narrowing option in v1 (custom ranges below), so this flag cannot succeed against the current published list; it fails loudly with its remedy instead of silently truncating.
- **Custom ranges:** cdn-scan v1 has **no custom-CIDR option** — no `--cidr` or `--ranges` flag exists. The target set is exactly Cloudflare's published CDN ranges. A user-supplied range that is not Cloudflare's published space is out of scope by design (Vision N3).

## 3. Ports & probe modes

Latency phase, two modes:

| Mode | Probe | Attempts | Default |
| --- | --- | --- | --- |
| `tcp` | TCP connect handshake to `ip:port`, timeout 1 s; four tries per endpoint, each try's result carried in the outcome's `AttemptRecord` | 4 (fixed, CFST `PingTimes`) | ✓ |
| `http` | HTTPS HEAD to `https://speed.cloudflare.com:<port>/`, connection pinned to the scanned IP (§3.1); timeout 2 s; valid codes 200/301/302; status and colo recorded in the outcome's `AliveDetail.facts` per §3.1 | 1 (fixed) | |

- Port is `--port` (default 443 both modes). http mode speaks TLS on that port; a plaintext `http://` request is never made.
- **Loss and liveness are carried by the outcome** (`01-architecture.md` §3.2): `ProbeOutcome { target, verdict, attempts: AttemptRecord, started_at }`, with `AttemptRecord { tries_made, tries_succeeded, try_rtts_us }`. The verdict is the liveness signal — `Alive { rtt, detail: AliveDetail }` or `Dead { reason }` — and `AliveDetail.facts` is the `BTreeMap<String, CellValue>` in which the probe records what it observed for `finalize`; in http mode those facts are the response status and colo (§3.1). cdn's fixed count makes `tries_made` = 4 in tcp mode (1 in http mode), `tries_succeeded` how many of those tries succeeded, and `try_rtts_us` each successful try's RTT. Loss = `(tries_made − tries_succeeded) / tries_made`; the reported `rtt_ms` is the mean of `try_rtts_us`, i.e. of the successful tries only. `finalize` computes both from that one record, so the `--max-loss` filter and the `loss_pct` column read the same field (§4 step 2, §6).
- `attempts` is the number of measurement tries the module makes for that endpoint — `tries_made` of the outcome's `AttemptRecord`, a fixed 4 in tcp mode and 1 in http mode — reported on every finding; it is a count of tries, never a retry budget, and any other value is a typed option error (§5, T2). Retry-versus-fixed is module policy under the shared probe model; cdn's policy is a fixed count, so a failed try is a **loss** and is never retried. **Liveness is the verdict, not the try count:** the probe emits `Alive` only when it observed a response (at least one successful try in tcp mode, the HEAD response in http mode) and `Dead` otherwise, and `finalize` reads the verdict rather than re-deriving liveness from `tries_made`/`tries_succeeded`. A `Dead` target is therefore never `filtered` — it has no RTT, so no filter bound can classify it (§4 step 2, §6).
- **IP pinning is non-negotiable** (research §4 cdn #4): without it, http mode measures the local resolver's favorite edge, not the scanned IP.
- `http` mode records `colo` (IATA from `cf-ray`) in the outcome's `AliveDetail.facts` and supports `--cfcolo FRA,HKG` filtering in the filter phase (CFST's killer feature for region-pinned users).

### 3.1 http mode pinning contract

1. The request targets a hostname, `speed.cloudflare.com` (v1 constant), never an IP literal; TLS SNI and the `Host` header are therefore `speed.cloudflare.com`.
2. The TCP connection is pinned to the scanned IP by a custom reqwest resolver/dialer that maps `speed.cloudflare.com` to that IP for every connection the target's client opens; system DNS is never consulted. A hostname URL is required: an IP-literal URL bypasses `resolve()`, presenting no SNI and a foreign Host.
3. **One client per target.** reqwest pools connections per host, so a client shared between targets could hand a pooled connection created for one target's IP to another target. v1 builds a client per target (pooling on, but never shared) and drops it after that target's requests. Cost: one TLS config + pool allocation per target, no handshake until first use; bounded by the http concurrency ceiling (≤ 200, §5).
4. `Connection: close` on the last request to a target. Dropping the client closes its idle connections; no pool or connection survives the scan (research §4 cdn #5, CFST PR #645; T5).
5. Redirects are not followed: a 3xx is a valid probe result, and following it would leave the pinned target.
6. Colo extraction requires **both** a `cf-ray` header and `server: cloudflare`; `colo` is the `cf-ray` suffix after the last `-`. When both are present the probe records the observed response in the outcome's `AliveDetail.facts` (`01-architecture.md` §3.2): `facts["status"] = Number(status)` and `facts["colo"] = Text("LAX")`. `finalize` reads `facts["colo"]` to fill the `colo` column and to apply the `--cfcolo` filter — the colo comes from the probe's facts, never re-derived from headers or a URL. A response missing either header is a failed HTTP probe (`Dead`), never a finding with `colo = ""`; no colo fact is recorded (T6). **This is policy, not detection:** an answer without both headers is counted dead **by policy** — stricter than CFST, and it marks a genuinely answering edge dead when a WAF/challenge response omits `cf-ray`, the usual case on hostile networks — so `--mode tcp` is the mode to use on such networks, because it judges reachability and latency without the header requirement.

## 4. Pipeline

Steps 2 and 3 run inside the module's `finalize` — the single outcomes→findings step, with no separate `summarize` (arch §5); core then orders the returned findings by `sort_rank`.

1. **Latency phase** (parallel): concurrency default 200; tcp ceiling 512, http ceiling 200 (`00-vision.md` §3.1). A value above the mode's ceiling is a typed option error, not a clamp or a warning (T2).
2. **Filter phase:** `--max-rtt` (default 200 ms, upper bound), `--min-rtt` (default 0 = off — the falsified-near-zero guard is the §4 step 5 proxy warning, not a hard floor), `--max-loss` (default 20%, upper bound). A target that responded is dropped when its result fails **any** one of the three: RTT > max-rtt, or RTT < min-rtt, or loss > max-loss; at the default `min-rtt` 0 the lower bound cannot fire, so no responder is dropped for answering fast. All three bounds read the outcome's `AttemptRecord` (§3): `finalize` takes RTT as the mean of `try_rtts_us` and loss as `(tries_made − tries_succeeded) / tries_made`, computes both once, and applies the bounds and the `loss_pct` column from those values — no second derivation, so the filter and the reported number cannot disagree. In http mode `--cfcolo` also applies, read from the probe's recorded colo fact: a missing `facts["colo"]` or a non-matching value → dropped (§3.1). The filter runs on measured RTT/loss after the latency phase and **before** the download phase; the download phase sees only `ok`, unfiltered findings (T3). A `Dead` verdict has no RTT: no filter bound can classify it, it produces **no finding row**, and core counts it in the totals (`dead = probed − alive`, §6). A target that responded but breached a bound stays `alive` and remains a finding marked filtered (`is_filtered() == true`) with its `status` still `ok` — `alive` means "responded" and `filtered` is the subset of responders this phase discarded (§6). Every responded target keeps its finding whether or not the frontend renders it (§6).
3. **Download phase (opt-in, `--speed`):** sequential over `ok` findings in ascending `sort_rank` order, using the rank snapshot taken when the phase starts — the ranks change once `speed_mb_per_s` is known, so the phase never re-reads a rank it has already passed.
   - `--speed-count` (default 10, max 10 — Vision §3.1) is the number of results the phase must produce. One rule per mode of `--speed-min`:
     - **`--speed-min` = 0 (no floor, the default):** the phase measures exactly `min(--speed-count, |ok findings|)` candidates, and the measured candidates **are** the results — every candidate it measured reports its speed, with no early stop on speed. When the `ok` pool is smaller than `--speed-count`, it measures every candidate that exists, stops short of the count, and emits one Log event naming how many candidates it measured and that `--speed-count` was not reached (T7).
     - **`--speed-min` > 0 (a floor):** the phase measures up to `min(|ok findings|, 10)` candidates in rank order, stopping early once `--speed-count` candidates have each measured ≥ the floor. When the `ok` pool runs out before that, it stops there and emits one Log event naming how many candidates it measured and that the floor was not reached (T7).
     - **The cap of 10 applies to measured candidates in both modes**, never to floor-meeting ones: a floor scan cannot keep spending candidates past the 10th in search of a qualifying count. With `--speed-count` at its 10 maximum, the required count and the measured cap coincide, so a floor scan that misses the floor on some candidates still ends at 10 measured.
   - GET a large file **through the pinned IP** (default URL: `https://speed.cloudflare.com/__down?bytes=100000000` — Cloudflare's own speed test endpoint, replacing CFST's third-party redirector default; override via `--speed-url`, hostname taken from the URL). Same pinning/client contract as §3.1.
   - 10 s per candidate (`--speed-time`), measured from the first body byte.
   - **EWMA:** received bytes are sampled every 100 ms; `s ← 0.25·x + 0.75·s`, where `x` is the window's MB/s and `s` is initialized to the first window's rate. The reported `speed_mb_per_s` is `s` — the smoothed rate, not the last instantaneous sample (T7). 1 MB = 1,000,000 bytes.
   - **Byte budget:** `--speed-max-bytes` (default 512 MB = 512,000,000 bytes; ceiling 512 MB, Vision §3.1). Each read is bounded by `min(buffer, remaining)` **before** it is issued, where `remaining` is the budget minus the bytes already received for the scan, so the cumulative total never exceeds the cap — no chunk past 512,000,000 bytes. `truncated: true` marks the finding whose download that bound cut: when `remaining` is zero the download ends, that finding is reported with `truncated: true`, and the phase stops (T7).
   - **Origin-IP guard (CFST's documented false positive):** candidates whose download errors or whose final smoothed rate is < 0.01 MB/s are marked `origin-suspect` (passes TCP/TLS, serves no useful body), unranked (`sort_rank` = `None`: listed after every ranked row, still present in output), and never count toward the `--speed-count`/floor stop condition.
   - Each candidate's client is dropped after it is measured (§3.1), so no connection is reused across candidates.
4. **Warm-up:** each target's probe performs one warm-up connect before its measured attempts (TCP connect in tcp mode, TLS connect in http mode, pinned in http mode). The warm-up is not an attempt: it is excluded from the outcome's `AttemptRecord` (no `tries_made` slot, no `try_rtts_us` entry) and from loss, and is not reported; its failure is ignored, since the measured tries decide. Under the probe time model (`01-architecture.md` §5) that warm-up connect is cdn's fixed `overhead` — 1 s in both modes — so the probe's total cap is `per_probe_timeout` = `overhead` + `max_attempts` × `per_attempt_timeout` (`timeout-per-probe`): 1 + 4 × 1 = **5 s** in tcp mode, 1 + 1 × 2 = **3 s** in http mode. The warm-up counts toward the charged-packet budget — one warm-up connection per target (§5). No measured attempt is discarded anywhere — not in the probe, not in `finalize` (Vision P3; T8).
5. **Proxy detection (warning only):** if > 90% of latency results are within 2 ms of each other and < 5 ms absolute, emit a Log warning "results suggest a local TUN-mode proxy is falsifying latency" (CFST gotcha #2; heuristic, advisory only).

## 5. Options

| Option | Type | Default | Notes |
| --- | --- | --- | --- |
| `mode` | enum | `tcp` | `tcp`/`http` |
| `port` | int | 443 | 1–65535; http mode speaks TLS on this port |
| `attempts` | int | 4 (tcp) / 1 (http) | number of measurement tries per endpoint — fixed per mode (CFST `PingTimes`), not a retry budget; reported per finding; the `AttemptRecord` carries `tries_made`/`tries_succeeded`/`try_rtts_us`, and liveness is the probe's verdict, not the try count; any other value → typed option error |
| `v6` | bool | false | add the published v6 ranges to the plan |
| `v6-samples` | int | 16 | random addresses per published v6 CIDR; ignored without `v6`; < 1 → typed option error |
| `all-ips` | bool | false | full v4 enumeration; rejected unless the plan's charged packets stay ≤ 250,000 and endpoints ≤ 64,512 (§2.2) |
| `sample-per-subnet` | int | 1 | 1–256: a /24 admits at most 256 distinct addresses, so N is deduplicated within the /24 and a value > 256 is a typed option error, never a silent clamp (T2) |
| `concurrency` | int | 200 | ceiling 512 tcp / 200 http (`00-vision.md` §3.1) |
| `timeout-per-probe` | ms | 1000 tcp / 2000 http | **per-attempt** timeout, floor 200; the probe's total cap is `per_probe_timeout` = `overhead` + attempts × this (tcp: 1 + 4 × 1 = 5 s; http: 1 + 1 × 2 = 3 s, `01-architecture.md` §5) |
| `max-rtt` / `min-rtt` | ms | 200 / 0 | filter bounds; `min-rtt` 0 = off — a floor above a healthy network's 5–20 ms nearest-PoP RTT would drop every finding and leave an empty table with `alive = filtered`, so the §4 step 5 proxy warning is the falsification guard and a user who wants the floor sets `--min-rtt` explicitly |
| `max-loss` | % | 20 | filter |
| `cfcolo` | list<str> | — | http mode only; post-filter on the probe's recorded colo fact (§3.1) |
| `speed` | bool | false | enable the download phase |
| `speed-count` | int | 10 | 1–10; results required (§4 step 3) |
| `speed-time` | s | 10 | per candidate, from first body byte |
| `speed-min` | MB/s | 0 | early-stop floor; help text: "download-rate floor in MB/s (1 MB = 1,000,000 bytes); 0 disables the early stop" |
| `speed-max-bytes` | MB | 512 | 1–512; download-phase byte budget (Vision §3.1) |
| `speed-url` | url | cf `__down` | must be `https://`; hostname is the pinning host |
| `scan-timeout` | s | 180 | wall-clock ceiling for the whole scan, **including the download phase**, matching Vision S3's 180 s bound; below the plan's feasibility floor → typed plan error naming the floor and, for `--speed`, the `--scan-timeout` that satisfies it (`--speed` at defaults needs ≥ 250) (§5 invariants, T2) |

**Invariants:**

- **Charged packets:** `charged_packet_count` (the `TargetPlan` field, `01-architecture.md` §5) = endpoints × (`attempts_per_probe` + `warmups_per_probe` + `noise_datagrams_per_probe`), ceiling 250,000 packets per scan. cdn sends no noise traffic, so at defaults the formula is 5,956 × (4 + 1 + 0) = **29,780 packets** in tcp mode (5,956 × (1 + 1 + 0) = 11,912 in http mode) — 5 charged packets per endpoint in tcp, 2 in http (§4 step 4). Above 250,000 the plan is `ScanError::InvalidPlan` (`01-architecture.md` §9; §2.2, T2).
- **Binding target bound:** the result lane holds 65,536 events (`01-architecture.md` §3.1), one per endpoint, and a full lane aborts the scan (`ScanError::ResultLaneOverflow`) — but the lane also carries the `Started`, `Phase`, `Log` and `Done` control events, so the endpoint bound is **64,512**: 65,536 minus a **1,024-event allowance** for those control and log events. A plan at exactly 65,536 endpoints is already over the line before the scan emits its first `Log`, and the allowance is not slack to spend on more endpoints. A plan whose endpoint count exceeds 64,512 is rejected at plan time with `ScanError::InvalidPlan` (exit 3) — the message naming the computed endpoint count, the 64,512 endpoint bound and the 1,024-event control allowance — so `--mode http --sample-per-subnet 11` (65,516 endpoints, 131,032 charged packets, inside 250,000) fails in `plan()` instead of streaming ~64k results and aborting mid-scan as `ResultLaneOverflow` (exit 6); that overflow stays the runtime backstop for a count that slipped past `plan()`, never the intended path for a plan the bound can refuse (T2). Both frontends drain the lane continuously — the lane is never buffered. Both bounds apply: at 5 charged packets per endpoint tcp mode is packet-bound at ≤ 50,000 endpoints; at 2 per endpoint http mode would fit 125,000 packets-wise, but the lane binds first at ≤ 64,512 (64,512 × 2 = 129,024 charged packets, inside 250,000). `--all-ips` needs 1,524,736 endpoints → 7,623,680 charged packets, so the packet ceiling rejects it (§2.2, T2).
- **`scan-timeout` ≥ the plan's feasibility floor, for the whole scan:** the latency phase needs `ceil(addresses / concurrency) × ports_per_address × per_probe_timeout` (`01-architecture.md` §5, §8) — `per_probe_timeout` is the probe's total cap (5 s tcp / 3 s http at defaults), never `timeout-per-probe` on its own — and when `--speed` is enabled the download phase adds its worst case: `min(--speed-count, 10) × --speed-time` when `--speed-min` is 0, and `10 × --speed-time` when `--speed-min` > 0, because a floor scan may measure up to `min(|ok findings|, 10)` candidates (§4 step 3) but never more than 10. At defaults the term is 10 × 10 s = 100 s either way. A `--speed` scan whose resolved `scan-timeout` is below that total is rejected at plan time as `ScanError::InvalidPlan` naming the floor and the flag that satisfies it (`--scan-timeout 250` at defaults); the 180 s default is never raised implicitly, so a `--speed` scan that passes no ceiling fails loudly with that remedy rather than being cut off mid-download, and the 180 s default is enough only for the latency phase. Latency phase at defaults: ceil(5,956 / 200) = 30 waves × 1 port × 5 s = 150 s, inside 180 s. A default `--speed` scan therefore needs 150 s + 100 s = **250 s**, so `--scan-timeout` ≥ 250.
- Concurrency ≤ the mode ceiling (512 tcp / 200 http, Vision §3.1); above it → `ScanError::OptionsInvalid { .. }` (exit 1) in plan-time option validation (arch §8, T2). Each ceiling has one owner: this module owns the stricter per-mode value and returns `OptionsInvalid` for a value above it, while core's 4,096 hard ceiling is a runner-construction backstop returning `ScanError::InvalidPlan` (exit 3) before any probe opens (arch §5) — not a plan-time check here, so the two variants never fire for the same value (513 and 5,000 are both this module's `OptionsInvalid` — both exceed the declared ceiling, and the value never reaches core; core's 4,096 backstop is reachable only from a module that declares no ceiling or one above 4,096, and is exercised by C7 at the constructor, `01-architecture.md` §5, §11).
- `cfcolo` without `mode=http` → typed option error.
- `speed-count` outside 1–10, `speed-max-bytes` outside 1–512 MB, `sample-per-subnet` outside 1–256, a non-https `speed-url`, or `attempts` other than the mode's fixed value → typed option error (T2).
- **Validation order is options → range → budget → identity** (arch §3): the range check runs before the packet-budget check, so the budget is never computed over addresses that failed the range check. The core allowlist is that range check and validates every plan; it can only fail here on a corrupted bundled snapshot, because cdn-scan accepts no custom input (Vision N3) — and when it does, the failure surfaces before any charged-packet arithmetic.

## 6. Output findings

Per-endpoint finding (implements arch §4 `ModuleFinding`). cdn probes one port per address (`--port`), so an address and an endpoint coincide here: the counts below are the same number either way. The module declares its result columns with `fn columns(&self) -> &[ColumnSpec]` (arch §5), `ColumnSpec { key, header }`; the CLI table and CSV render exactly those columns in declared order, and each finding's `to_row()` emits exactly those keys (arch §4). `FindingRow` carries the declared keys and nothing else, and an inapplicable field is `CellValue::Null`. The keys are defined once here and inherited by the table, CSV and JSON:

| Key | Header | Value |
| --- | --- | --- |
| `ip` | IP | the scanned address (one endpoint per address, §3) |
| `rtt_ms` | RTT (ms) | mean of the outcome's `try_rtts_us` — the successful tries only (§3) |
| `loss_pct` | Loss (%) | `(tries_made − tries_succeeded) / tries_made × 100` from the outcome's `AttemptRecord` — the same field `--max-loss` filters on (§3, §4 step 2) |
| `attempts` | Attempts | tries the module made for this endpoint — `tries_made` of the `AttemptRecord`, 4 tcp / 1 http, fixed (§3) |
| `port` | Port | the probed port (`--port`, 443 by default) |
| `colo` | Colo | the probe's recorded colo fact (`AliveDetail.facts["colo"]`, §3.1); null when the probe recorded none (http mode only) |
| `speed_mb_per_s` | Speed (MB/s) | EWMA-smoothed rate; null unless `--speed` measured this endpoint (§4 step 3) |
| `truncated` | Truncated | true only when the byte budget cut this endpoint's download (§4 step 3) |
| `status` | Status | `ok` / `origin-suspect`; never encodes filtering (§4 step 2) |

- `speed_mb_per_s` is the EWMA-smoothed rate in MB/s (1 MB = 1,000,000 bytes/s, §4 step 3). `truncated` is true only when the scan byte budget cut that candidate's download; false when the 10 s window or EOF ended it.
- `colo` is null unless http mode and the probe recorded a colo fact — both pinning headers present (§3.1); `finalize` never re-derives it.
- **Ordering (core contract):** `ModuleFinding::sort_rank(&self) -> Option<u64>` — `Some(rank)` sorts ascending; `None` is unranked, listed after every ranked row, and never excluded from the output. `ok` findings return `Some(rank)`; `origin-suspect` returns `None`, so it is listed after every `ok` row while staying in `findings` and in JSON (§7 T7; 04-cli §3, §8 T7). Only the **relative order** is contractual, not the numeric encoding: core sorts by the `Option<u64>` rank it is given, and the module computes that rank so that findings with a measured speed rank before findings without one, among those with a speed the faster first, and ties are broken by ascending RTT. A filtered finding keeps its `ok` status and its rank; the filtered flag is a separate, shared concept (§4 step 2).
- **Filtered rows:** an endpoint that responded always produces a finding; when it breached a filter bound it stays in the model marked `is_filtered() == true` (`ModuleFinding::is_filtered`, default `false`) while its `status` stays `ok`. Filtered findings are hidden from the default CLI table and CSV unless the `--show-filtered` toggle (04-cli §2) is on; JSON always includes them (04-cli §3).
- **Dead endpoints:** an endpoint with a `Dead` verdict (zero successful tries) produces **no finding row** — core counts it as `dead` (`probed − alive`) and reports that in the totals only, never as a finding (T3). Findings therefore exist only for `alive` endpoints, and `filtered ⊆ alive` follows from that.
- **JSON** (04-cli §3 shape): `{module, started_at, wall_time, totals, findings}`, where `module` is `cdn`, `findings` serializes the columns above, and `totals` is exactly `{probed, alive, filtered, cancelled}` (04-cli §3). Findings exist only for `alive` endpoints; `filtered` refines `alive` and is never a third bucket:
  - `probed` = endpoints attempted.
  - `alive` = endpoints with an `Alive` verdict (= the number of findings).
  - `dead` = `probed − alive` (endpoints with a `Dead` verdict); never serialized, never a finding row.
  - `filtered` ⊆ `alive` — the findings marked `is_filtered() == true`: endpoints that responded but whose result the filter phase dropped (over `max-rtt`, under `min-rtt`, over `max-loss`, `--cfcolo` mismatch, §4 step 2). The module's own `status` column keeps its own vocabulary (`ok | origin-suspect`); the shared filtered notion is `is_filtered()`, never a status string, so core never interprets a module's status strings.

  `cancelled` is a bool, true when the scan ended before its plan completed — a user cancel or budget exhaustion (`01-architecture.md` §4, §8; `04-cli.md` §4). Therefore `probed = alive + dead` exactly, `filtered ≤ alive`, and no counter can go negative.

## 7. Success tests (module level)

- T1: unit — sampler over fixture range sets: one IP per /24, correct counts, dedup at `sample-per-subnet` > 1; with `--v6`, N random-tail addresses per v6 CIDR, deduplicated, and none without `--v6`; `--all-ips` expands exactly on a fixture plan that stays under the packet ceiling.

The missing-`facts["colo"]` branch of the §4 step 2 colo filter is unreachable through http mode, because §3.1 turns a header-less answer into `Dead` and so into no finding at all (a): the drop is exercised by a non-matching colo, never a missing one.
- T7: unit — download phase over a synthetic byte feed and clock: EWMA of a known window sequence equals the expected smoothed value and is what gets reported; `--speed-min` 0 measures exactly `min(--speed-count, |ok findings|)` candidates with no early stop and every measured candidate is a result (`--speed-count` 10 over 5 ok findings → 5 measured, 5 reported); with `--speed-min` > 0 and `--speed-count` 3 the phase stops after the third floor-meeting candidate without touching later ranks, having measured at most 10 candidates; with a floor set and `--speed-count` 10 the phase measures at most `min(|ok findings|, 10)` candidates even when fewer than 10 meet the floor, stops when the pool runs out, and emits one Log event naming how many it measured and that the floor was not reached; with fewer `ok` findings than `--speed-count` (`--speed-count` 5, 2 ok findings) the phase measures those 2, stops short of the count, and emits one Log event naming 2 measured candidates and that `--speed-count` was not reached; budget exhaustion cuts the in-flight download, sets `truncated: true` on that finding, and the cumulative downloaded bytes never exceed the budget; an origin-suspect finding in the synthetic set returns `sort_rank()` = `None` and `finalize` lists it after every ranked row while keeping it in `findings`.
- T8: unit — warm-up and the attempt record: the probe harness observes one warm-up connection plus exactly 4 measured tcp attempts, the outcome's `AttemptRecord` holds `tries_made` = 4 with one `try_rtts_us` entry per successful try, and the `attempts` column shows 4; `finalize` derives loss as `(tries_made − tries_succeeded) / tries_made` and `rtt_ms` as the mean of `try_rtts_us`, so 3 successes out of 4 report loss 25% and the mean of those 3 RTTs, and a finding cut by `--max-loss` at that value carries 25% in `loss_pct` — filter and column are one field; when the warm-up fails, `tries_made` stays 4, all 4 tries succeed and loss stays 0; `finalize` discards no measured attempt.
